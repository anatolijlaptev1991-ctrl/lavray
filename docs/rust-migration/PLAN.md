# План переноса Go-части LAVRay на Rust (упор на производительность)

Дата: 2026-11-08. Документ для владельца. Код и репозиторий не менялись, приложение не запускалось.

Источники: факты по крейтам, протоколам, бенчмаркам и лицензиям взяты из `docs/rust-migration/research-2026-11-08.md` (далее «исследование»); архитектура сверена с кодом в `lavray/` (ссылки ниже); контекст оптимизаций оболочки и UI — внешний отчёт аудита 2026-11-07 (не в репозитории) (далее «аудит»). Всё, что не подтверждено источником, помечено **ДОПУЩЕНИЕ** или **НЕ ПРОВЕРЕНО**.

---

## 1. Краткий вывод

1. **Скорость туннеля определяет data plane, а не control plane.** Протоколы, TUN на gVisor, DNS, маршрутизация, uTLS/REALITY и QUIC выполняет sing-box (Go-библиотека, форк в `core/go.mod`). Control plane (api, store, cfgbuild, subs, links, presets, mcp, web, updates, backup, logs, traffic) на горячем пути пакетов почти ничего не стоит. Его перенос на Rust даёт один язык и процесс, меньше памяти и задержек UI, но **не ускоряет туннель**.
2. **Опубликованных сравнений «Rust-прокси против sing-box» нет** (исследование, бенчмарки п.3). Единственный свежий замер — meow-rs против Go-mihomo (не sing-box, loopback, один хост, самоописание): пропускная способность на уровне, RSS в 3 раза меньше, p99 ниже. shadowsocks-rust в бенчмарке 2022 года **медленнее** Go-реализации. Выигрыш data plane нужно **доказать замерами**, а не предполагать.
3. **Стратегия: «душитель» по контракту `proto/lavray.proto`.** UI не меняется. Rust-реализации сервисов ConnectRPC заменяют Go по частям; на каждом шаге Go↔Rust сравниваются дифференциальными тестами на одних входах.
4. **Порядок: R0 базовая линия → R1 Rust control plane при Go-движке → R2 ворота решения по data plane → R3 постепенный перенос → R4 удаление Go.** R1 даёт ценность независимо от исхода R2. R4 допустим только после прохода R2/R3.
5. **Гибрид «Rust control plane + sing-box движок» — полноценное финальное состояние**, если ворота R2 не пройдены. Это не провал плана.
6. **Главный риск — паритет анти-цензуры** (отпечатки uTLS/REALITY, поведение в сетях РФ), затем Windows TUN/маршрутизация (`strict_route`, kill-switch). Ни один Rust-кандидат не подтверждён как замена sing-box по этим пунктам (исследование, разделы «Не подтверждено»).
7. **Оценка:** R0 около 3–5 агенто-недель, R1 около 35–60, R2 около 12–25, R3 около 20–45, R4 около 10–20 (допущения в разделе 9). R1 параллелизуется по пакетам; R2 может стартовать до конца R1.
8. **Дешёвые выигрыши не ждут миграции.** Аудит нашёл реальные узкие места control plane. В 0.9.2 уже исправлены `GetStatus` (6 SQL-чтений вместо 51), конвейер логов Go (`sblog.go`, `max_lines_per_second`, атомарный `Tail`) и `GetTrafficTotals`; остался `ListProfiles` (полная загрузка + `json.Unmarshal` каждой строки; в UI уже debounce и отмена устаревших запросов). Его можно исправить в Go сейчас; а при переносе нужно переносить **исправленный дизайн**, иначе дефекты копируются в Rust.

## 2. Текущая архитектура (по коду)

### 2.1. Процессы и владение

```
Tauri-оболочка (Rust, shell/src, ≈22 тыс. строк) ── UI (React, WebView, ui/src, connect-web)
        │ spawn + stdin-токен + READY-строка            │ ConnectRPC (JSON), Bearer-токен
        ▼                                               │
lavray-core (Go, core/cmd/lavray-core) ◄────────────────┘   сокет/pipe/127.0.0.1:0
        └── sing-box в ТОМ ЖЕ процессе (box.New), TUN, DNS, маршруты
```

Каждый пункт — по коду:

- **Spawn-протокол** (`shell/src/coreproc/driver.rs`, шапка файла; `core/cmd/lavray-core/main.go`, шапка): argv `serve --listen-socket <unix:///…|\\.\pipe\…|127.0.0.1:0> [--data <dir>] [--headless] [--web-bind … --platform openwrt]`; cwd = каталог данных (права 0700).
- **Токен**: 32 байта CSPRNG → base64url → **первая строка stdin**; вторая необязательная строка — агентский токен MCP (`core/cmd/lavray-core/stdin.go`, `readStartupStdin`). Токен никогда не в argv/env. **stdin держится открытым; EOF = «оболочка умерла» → graceful-выход ядра.**
- **READY**: одна строка в stdout `LAVRAY_CORE_READY <transport-url>` (`driver.rs:41`, `READY_LINE_PREFIX`; `main.go:44`). Бюджет ожидания `T_READY_BUDGET` = 2 с, предупреждение через 5 с (`coreproc/mod.rs:27-29`). Далее оболочка проверяет `/healthz` с Bearer.
- **Управление процессом ядра в оболочке**: Windows — `CREATE_NO_WINDOW` + Job Object `KILL_ON_JOB_CLOSE`; Unix — своя process-группа и `PR_SET_PDEATHSIG`. Kill-лестница §5: EOF на stdin → `CoreService.Disconnect` → `Shutdown` → SIGTERM/`TerminateJobObject` → SIGKILL (`driver.rs`, шапка). Логи stdout/stderr — построчно в `LogRing` (200 строк) с антифлудом (`coreproc/logs.rs`).
- **Агент (MCP)**: `lavray-core mcp` подключается к запущенному приложению по `agent-endpoint.json` (`mcp_cmd.go`; `shell/src/agent.rs`, `endpoint.rs`).
- **Режимы без оболочки**: `--headless` (`internal/headless`, 84 строки: `ConnectLast` + авторестарт), `--web-bind` (веб-панель, `internal/web`), `--platform openwrt` (шлюз с `nft -f -`, `internal/gateway`, `cmd/lavray-core/ext_gateway.go`).

### 2.2. Как UI ходит в ядро

- `ui/src/lib/core.ts`: `createConnectTransport` из `@connectrpc/connect-web` (v2.2), **`useBinaryFormat: false` — JSON-кодек**; авторизация перехватчиками (Bearer или cookie+CSRF для веб-режима, `coreAuth.ts`). Адрес ядра оболочка передаёт в `window.__LAVRAY_CORE_URL`.
- Контракт: `proto/lavray.proto` — 2 411 строк, 16 сервисов, 95 RPC, из них **10 server-streaming** (`SubscribeEvents`, `TestLatency`, `UpdateSubscription`, `UpdateAllSubscriptions`, `SubscribeSettings`, `LogService.Subscribe`, `StatsService.Subscribe`, `WatchConnections`, `DownloadUpdates`, `ApplyUpdates`). Клиентских/двунаправленных стримов нет.
- Следствие для Rust-сервера: нужен Connect-протокол (unary + server streaming) в **JSON-кодеке** поверх HTTP/1.1 и/или h2, с каноническим proto3-JSON (имена полей, `int64` строками, enum строками, `Any`/`Timestamp`), на UDS/named pipe/TCP-loopback.

### 2.3. Где ядро использует sing-box

Прямой `import github.com/sagernet/sing-box` — **6 не-тестовых файлов** (исследование, часть 1):

| Файл | Что делает |
|---|---|
| `internal/inst/singbox.go` (за тегом `singbox_run`) | `box.New(box.Options)`, `Start`/`Close`, `include.Context`; реализует `inst.Runner` (`Start(ctx, configJSON)`, `Stop(ctx)`, `inst.go:98`) и `ProxyDialer` (`DialProxy`) |
| `internal/inst/platform_writer.go` | перехват журнала sing-box через `SetLogWritter` (reflect/unsafe) |
| `internal/inst/trackmeta.go`, `traffic_singbox.go` | адаптер `trafficcontrol.Manager` → `traffic.Source` (соединения, байты) |
| `internal/inst/testinst.go` | тестовый инстанс, `NekoDialContext`/`NekoDialUDP` (патч форка `box_neko.go`) |
| `internal/api/ruleset_singbox.go` | разбор `.srs` через `srs.Read` |

Конфиг передаётся **только через память**: `cfgbuild` собирает `map → JSON` без импорта sing-box (LNB-18), `inst.Runner.Start(ctx, configJSON)` отдаёт его в `box.New`. Это идеальный шов: он **уже** является узким интерфейсом «JSON внутрь».

Состав сборки: теги `singbox_run,with_quic,with_gvisor,with_utls` (`core/BUILD_TAGS`). Точный набор протоколов и функций LAVRay — в исследовании, часть 1 (не дублирую): SS (18 методов, 2022, plugin, UoT), VMess, VLESS+Vision, Trojan, Hy2 (salamander, hop), TUIC v5, SOCKS/HTTP; транспорты tcp/ws/http/grpc(lite)/httpupgrade/quic; TLS, REALITY, uTLS-профили; sing-mux h2mux; TUN (gvisor по умолчанию, `strict_route`), FakeIP, DNS (local/udp/tcp/tls/https/h3/quic), rule-set `.srs`, process_name, sniff, hijack-dns. XHTTP — `transport_unsupported`. WireGuard, ShadowTLS, AnyTLS, SSH, Tor, ECH — не используются.

### 2.4. Что делают остальные части

- **headless** — цикл «подключить последний профиль, при падении перезапустить через 3 с» (`headless.go`, интерфейс `CoreAPI`). Тривиально переносится.
- **web** — веб-панель: аутентификация (argon2id, pbkdf2), CSRF, лимитер, cookie, origin-проверки (`internal/web`, 1 825 строк); раздаёт `web/dist`.
- **gateway** — OpenWrt: рендер правил nftables (`nft_render.go`), применение через `nft -f -` (`nft_apply.go`), watchdog, политики (`internal/gateway`).
- **mcp** — MCP-сервер, написан вручную (JSON-RPC, версии протокола 2024-11-05 / 2025-03-26 / 2025-06-18), tools чтения/управления.
- **updsign** (`cmd/updsign`, 1 545 строк) — инструмент подписи релизов: minisign-подобные подписи, manifest, geopack, TUF-lite роли (`verify_role.go`, `resign.go`). Клиентская проверка — `internal/updates` (root.json с threshold, timestamp.json, ed25519/ecdsa/rsa/x509/blake2b, `rootchain.go`, `staging.go`, `dirswap.go`).
- **store** — SQLite через `modernc.org/sqlite` (CGO-free), WAL, `foreign_keys` в DSN (`store.go:64-76`), миграции (`migrate.go`), импорт NekoBox (`nekoimport`, 2 153 строки), восстановление из бэкапа (`restore*.go`).
- **backup** — формат LAVBK1 (magic, заголовок, argon2 + XChaCha20-Poly1305, `keycheck` = HMAC-SHA256; `backup/header.go`).

### 2.5. Что уже оптимизировано / известно из аудита

Внешний отчёт аудита 2026-11-07 (не в репозитории) относится в основном к оболочке (Rust) и UI и **явно** не проверял реальную VPN-нагрузку («реальная VPN-нагрузка и end-to-end скорость не проверялись»). Для миграции важны три вывода:

1. Узкие места **Go control plane**, найденные аудитом (в 0.9.2 исправлены логи, `GetStatus`, `GetTrafficTotals`; `ListProfiles` и `WatchConnections` на стороне ядра — нет): конвейер логов (`sblog.go`: append до проверки `maxPendingLine`; `max_lines_per_second` объявлен в proto, но `Subscribe` его не читает; регистрация и `Tail` не атомарны), `ListProfiles` (полная загрузка до фильтрации), `GetStatus` (51 SQL-чтение, статический расчёт), `GetTrafficTotals` (игнорирует `profile_ids`), `WatchConnections` (полная сортировка на кадр).
2. Цифры аудита («11,02×», «11,88×» и т. п.) — **model-only** и относятся к Rust-оболочке; переносить их на ядро или на data plane нельзя.
3. Часть улучшений меняет контракт ошибок (batch all-or-nothing) — это решение владельца, а не техническая деталь.

## 3. Цели и что считается «максимальной производительностью»

«Максимальная» здесь — не лозунг, а набор метрик с базовой линией. Нет базовой линии — нет утверждения о выигрыше.

### 3.1. Метрики data plane (определяют скорость VPN)

| Метрика | Как измеряется | Единица |
|---|---|---|
| Пропускная способность TCP, 1 поток и 10 потоков, вверх/вниз | iperf3 через прокси-цепочку, для каждого класса протокола | Гбит/с |
| Пропускная способность UDP через TUN | iperf3 -u с контролем потерь ≤ 0,1 % | Мбит/с |
| CPU на Гбит/с | `ETW`/`perf stat`, доля одного ядра при фиксированной скорости | % ядра / (Гбит/с) |
| Память | RSS в простое; RSS при 1000 одновременных соединений; рост за 72 ч | МБ |
| Задержка | p50 и p99 RTT малых запросов через туннель (HTTP 1 КБ, DNS) | мкс/мс |
| Время старта | от команды Connect до готовности TUN и первого пропущенного пакета | мс |
| Устойчивость | 1000 соединений, 72 ч, без утечек и паник | — |
| Анти-цензурное качество | совпадение ClientHello с Chrome, доля успешных соединений в РФ-сетях | % |

### 3.2. Метрики control plane (определяют отзывчивость UI и ресурсы)

RSS ядра в простое и под нагрузкой UI; p50/p99 unary-RPC (`GetStatus`, `ListProfiles` на 10 тыс. профилей); время старта ядра до `LAVRAY_CORE_READY` (сейчас бюджет 2 с); пропускная способность лог-потока без потерь; размер бинаря (OpenWrt); время холодной сборки.

### 3.3. Что принимается за «лучше»

Сравнение всегда **парное**: тот же стенд, то же железо, то же ядро ОС, минимум 10 прогонов, медиана и 95 %-ный доверительный интервал, коэффициент вариации. Результат внутри шума (разница меньше CV) трактуется как «равно». Loopback-замеры (как в README meow-rs) годятся для отбраковки, но **не** для решений: решения — по двухузловому стенду (клиент и сервер на разных машинах).

## 4. Фазы

### R0. Подготовка и базовая линия

**Цель.** Заморозить контракты и получить цифры текущего sing-box, с которыми будут сравниваться все следующие шаги.

**Работы.**

1. **Заморозка контрактов.** Зафиксировать хэш `proto/lavray.proto` и политику изменений (только обратно-совместимые добавления до конца R3). Добавить в CI проверку `buf breaking` (**ДОПУЩЕНИЕ**: `buf.gen.yaml` в репозитории есть, значит buf используется; `buf breaking` настроить).
2. **Выгрузка корпусов и golden из Go-тестов** в нейтральный каталог `lavray/conformance/` (JSON/бинарные файлы, не Go-код), чтобы Rust-тесты читали **те же** файлы:
   - корпуса фаззинга: `links/fuzz_test.go`, `presets/fuzz_test.go`, `store/nekoimport/fuzz_test.go`, `subs/happ/fuzz_test.go`, `backup/*_test.go`, `model/canonjson_test.go` + `testdata/` пакетов `links`, `subs`, `store`;
   - golden cfgbuild: `cfgbuild/testdata/golden/` (74 файла) и `deviations.yaml`;
   - фикстуры миграций SQLite: `store/testdata/`, цепочка `migrate.go`;
   - образцы бэкапов LAVBK1 с известными паролями и ключами (сгенерировать Go-кодом: валидные, повреждённые, обрезанные);
   - метаданные TUF-lite: корректные, просроченные, с недостаточным threshold, с откатом версии, из `updates/updatestest/` и `updsign`.
3. **Дифференциальный харнесс.** Скрипт поднимает Go-ядро и Rust-ядро на одинаковых данных и сравнивает ответы RPC (JSON-тела) по списку вызовов; расхождения — в отчёт с категориями «ожидаемое» / «дефект».
4. **Стенд замеров data plane** (требует владельца: раздел 11):
   - два узла (клиент — рабочий ПК; сервер — второй ПК или VPS), тестовые серверы на sing-box и Xray для каждого протокола;
   - генераторы: iperf3 (TCP/UDP), `wrk`/`oha` для малых запросов, свой генератор 1000 соединений;
   - сбор CPU/RSS: ETW/WPR (Windows), `perf` (Linux/OpenWrt-класс), `/proc`;
   - замеры по каждому классу протокола: SS-2022, VLESS+REALITY+Vision, VMess/Trojan поверх WS+TLS, Hy2, TUIC, режимы inbound `mixed`/`socks` и TUN (`gvisor`, `system`, `mixed`).
5. **Профилирование текущего sing-box:** где тратится CPU (pprof Go + ETW) — это ответ на вопрос «что вообще можно ускорить» ещё до написания Rust-кода. Если 70 % CPU уходит в AES/ChaCha и копирование, а не в планировщик Go, потолок выигрыша мал; это решение должно быть принято по данным.
6. **Исправление известных узких мест control plane в Go** (по желанию владельца, вне критического пути): оставшийся `ListProfiles` и сортировка `WatchConnections` (логи и `GetStatus` исправлены в 0.9.2). Тогда базовая линия control plane отражает «лучшее возможное на Go», и Rust сравнивается с ним, а не с заведомо плохим кодом.

**Критерии готовности R0.**
- Каталог `conformance/` собран и загружается и Go-, и (заглушкой) Rust-тестом; число файлов корпусов зафиксировано.
- Протокол стенда и таблица базовой линии (все метрики из 3.1 по всем классам протоколов) опубликованы в `docs/rust-migration/baseline-*.md`, прогонов ≥ 10, CV указан.
- Профиль CPU sing-box с разбивкой «крипто / сеть / netstack / аллокации и GC / прочее».
- Решение владельца по контракту ошибок batch (аудит п.2) принято и записано.

**Риски R0.** Нет второго ПК — замеры только на loopback (решения по ним принимать нельзя); нестабильность замеров из-за антивируса и Windows Defender (исключения на время стенда); различие сетей (домашний канал даёт шум больше эффекта).

### R1. Rust control plane при Go data plane

**Цель.** Весь control plane — на Rust; Go остаётся только как «движок» sing-box. UI и оболочка не меняются.

#### 4.1.1. Целевая схема

```
Оболочка (Rust, без изменений) ──spawn/stdin/READY──► lavray-core (Rust, НОВЫЙ, тот же argv/READY/токен)
UI ──ConnectRPC JSON──► lavray-core (Rust)
                              │ внутренний API (UDS/pipe, токен через stdin)
                              ▼
                        lavray-engine (Go: sing-box + inst + traffic + ruleset + testinst)
```

- Бинарь Rust-ядра сохраняет имя, аргументы, поведение stdin/READY/`/healthz`, чтобы **`shell/src/coreproc` не менялся** (оболочка опирается именно на этот протокол). Подмена — копированием бинаря, с флагом отката на Go-ядро.
- `lavray-core` (Rust) становится супервизором движка по тем же правилам, что оболочка — ядра: токен через stdin, ready-строка, EOF на stdin = смерть родителя, Job Object / pgid / PDEATHSIG, kill-лестница. Готовый код — `shell/src/coreproc/{driver,runner,teardown,backoff}.rs` (около 2 300 строк): вынести в общий крейт `lavray-proc` и переиспользовать (**ДОПУЩЕНИЕ**: код достаточно изолирован для выноса; проверить в первой неделе).
- **Внутренний API движка** (`proto/engine.proto`, отдельный от публичного, не виден UI):

| Метод | Назначение | Источник в Go |
|---|---|---|
| `Start(config_json)` / `Stop` | запуск и остановка sing-box | `inst.Runner` |
| `DialProxy(network, addr)` | проверка связи через исходящее `proxy` | `inst.ProxyDialer` |
| `TestDial(config, targets)` | тест задержки отдельным мини-инстансом | `inst/testinst.go` |
| `StreamTraffic()` | события открытия/байт/закрытия соединений | `traffic_singbox.go`, `trackmeta.go` |
| `SnapshotConnections()` / `CloseConnection(id)` | список и закрытие | `trafficcontrol.Manager` |
| `StreamLogs()` | журнал sing-box | `platform_writer.go`, `sblog.go` |
| `ParseRuleset(srs_bytes)` | `.srs` → JSON правил (до порта в R4) | `api/ruleset_singbox.go` |

Транспорт — ConnectRPC/gRPC по UDS или named pipe (**ДОПУЩЕНИЕ**: те же библиотеки, что для публичного API, проще, чем свой формат; альтернативой служит простой length-prefixed protobuf — ради нескольких микросекунд не нужен). Статистика трафика — **агрегированными пакетами раз в 100–1000 мс**, а не по событию на пакет; иначе межпроцессный мост сам становится горячим путём.

- **Встраивание sing-box как c-shared библиотеки (libbox/FFI) в процесс Rust — рассмотрено, на переходный период отклонено.** Основания:
  1. *Домен падения.* Паника Go или fatal error рантайма (concurrent map write, OOM Go-кучи) убивает **весь** процесс, включая SQLite-транзакции, веб-панель и API; отдельный процесс-движок даёт перезапуск движка без потери control plane (headless-цикл уже умеет авторестарт).
  2. *Два рантайма в одном процессе.* Go-планировщик, GC и сигналы (в частности SIGPIPE, SIGSEGV-обработчики) конфликтуют с Rust-рантаймом; Go-сборщик не знает про память Rust. Профилирование и отладка смешанного процесса сложнее.
  3. *Сборка.* Нужен cgo с `-buildmode=c-shared`, на Windows — MinGW/clang и согласованная C-ABI; кросс-компиляция под OpenWrt (musl, aarch64) с cgo заметно тяжелее, чем сейчас (`CGO_ENABLED=0` для ядра, `store.go:20`). **НЕ ПРОВЕРЕНО** на практике.
  4. *Готовой основы нет:* официальные libbox — gomobile для Android/Apple, NuGet для Windows/C#; Rust-биндинга нет (исследование, строка «sing-box как библиотека»). Свой cgo-мост означает поддерживать форк-специфичный FFI.
  5. *Выигрыш мал:* вызовы идут на уровне «конфиг внутрь, агрегаты наружу», а не на уровне пакетов; издержки процессной границы (микросекунды на RPC, раз в 100 мс) несущественны.
  FFI имеет смысл пересмотреть только как **вспомогательный вариант для R3**, если замеры покажут значимую цену IPC на статистике соединений.

#### 4.1.3. Стратегия «душитель» по сервисам

1. До готовности всего `api` Rust-ядро не может заменить Go целиком (UI ходит на один адрес). Поэтому на переходе применить **маршрутизирующий фасад**: Rust-процесс принимает все RPC; для ещё не перенесённых сервисов проксирует в Go-ядро (тот же контракт, внутренний адрес), для перенесённых отвечает сам. Так Go-ядро живёт как «второй движок» до окончания переноса `api`, а затем сжимается до чистого engine (пункт 5 ниже).
   - **ДОПУЩЕНИЕ**: прокси Connect→Connect для unary и server-streaming на Rust реализуется тонким слоем (hyper); стоимость слоя измерить.
   - **Альтернатива**, если фасад окажется дорогим: переносить в порядке, при котором целые сервисы (например `BackupService`, `MigrationService`, `WebSessionService`) переключаются «одним рубильником» в конфиге UI/ядра.
2. На каждый сервис — три теста: (а) дифференциальный на фикстурах; (б) контрактный: Rust-сервер, Go-клиент и TS-клиент (`connect-web`) в одном прогоне; (в) нагрузочный на сравнение с базой R0.
3. Переключатель на сервис: `lavray-core --rust-services=...` (**ДОПУЩЕНИЕ**: имя флага условное) + немедленный откат на Go без миграции данных.
4. Общая БД: SQLite-файл **один**; пока одновременно живут Go и Rust, писать в него должен только один из них для каждой таблицы (WAL допускает параллельное чтение). Миграции схемы выполняет **один** процесс в каждый момент времени; Rust получает владение после переноса `store`.
5. Финал R1: `api`, `mcp`, `web`, `gateway`, `headless` на Rust; Go-бинарь `lavray-engine` — только sing-box + `inst` + `traffic` + `ruleset` + `testinst` (около 3 тыс. строк прод. кода плюс sing-box).

- Все 16 сервисов отвечают из Rust; Go-ядро больше не принимает запросов UI.

- Метрики control plane (3.2) не хуже Go-базы; RSS и p99 `ListProfiles`/`GetStatus` задокументированы (цель: улучшение, но **без числового обещания**).
- Оболочка и UI не менялись (diff в `shell/` и `ui/` пуст, кроме имён сборочных скриптов).
- Сборка под Windows x86_64 и OpenWrt (aarch64, x86_64) проходит; размер бинаря фиксируется (риск R-8).

**Риски R1.**
- Connect-RPC на Rust: `connectrpc` (connect-rust) — pre-1.0 (0.7.0), заявления о конформности — самоописание (исследование). Запасной путь: свой тонкий Connect-слой на hyper/axum + prost (протокол прост: unary POST `application/json`, стрим — envelope `application/connect+json`). Принять решение по результатам спайка в первые две недели.
- Паритет proto3-JSON (имена полей `lowerCamelCase`, `int64` в строках, значения enum, обработка неизвестных полей, `null`). Ловится дифференциальными тестами на JSON-телах.
- Работа с БД: пока один процесс пишет, второй не должен трогать схему.
- Двойной тест-объём: поддержка Go и Rust версий на время перехода.

### R2. Ворота решения по data plane

**Цель.** Решить, оправдан ли перенос data plane, **по данным**, а не по убеждению.

**Работы.**

1. **Прототип Rust-движка за тем же интерфейсом** (`engine.proto` из 4.1.1): процесс `lavray-engine-rs` реализует `Start(config_json)` для **подмножества** конфигов, получаемых от `cfgbuild`. Если конфиг содержит неподдерживаемое — `Start` возвращает типизированную ошибку `UNSUPPORTED(feature)`, а супервизор откатывается на Go-движок (основа для R3).
2. **Выбор базы** (кандидаты из исследования, не пересказываю таблицу): shoes, clash-rs, meow-rs, leaf; точечные крейты — shadowsocks-rust, quinn, rustls / boring (BoringSSL), netstack-smoltcp / ipstack (TUN), wintun-bindings (драйвер Wintun), hickory-dns (DNS). Решение «форк готового ядра или сборка из крейтов» принимается по результатам матрицы совместимости (п.3), а не заранее. **ДОПУЩЕНИЕ**: форк shoes или meow-rs требует меньше кода, чем сборка с нуля, но привязывает к чужой архитектуре; сборка из крейтов даёт контроль, но стоит дороже (оценки R2/R3 это отражают).
3. **Матрица совместимости по ТОЧНОМУ набору LAVRay** (раздел 2.3 / исследование). Строки — каждая возможность, столбцы — кандидаты; ячейка — результат **теста взаимодействия** с эталонным сервером (sing-box и Xray), а не README:
   - SS (18 методов, особо 2022-blake3-*; plugin; UoT v1/v2), VMess (alter_id, security auto/none/zero/aes/chacha), Trojan, VLESS + `xtls-rprx-vision`, Hy2 (salamander, hop, up/down), TUIC v5 (bbr/cubic/new_reno, native/quic, zero_rtt), SOCKS/HTTP;
   - транспорты: tcp(+http-заголовок), ws (early data `ed=`), http(h2), grpc, httpupgrade, quic;
   - TLS: sni/alpn/insecure/certificate; REALITY (pbk/sid); uTLS-профили chrome, firefox, edge, safari, 360, qq, ios, android, random, randomized;
   - sing-mux (h2mux, padding, concurrency);
   - chain через `detour`; `custom_outbound`/`custom_config` (сырой sing-box JSON — требует интерпретатора sing-box JSON, это **крупная** строка в матрице);
   - TUN (gvisor-эквивалент, `system`, `mixed`, `strict_route`, `auto_route`, kill-switch), inbound mixed/socks/http, FakeIP (198.18.0.0/15, fc00::/18), DNS (local/udp/tcp/tls/https/h3/quic, dns-правила с rule_set), rule-set `.srs`, process_name, sniff, hijack-dns, `auto_detect_interface`, `default_domain_resolver`.
   Строки, закрытые «не поддерживается» → **список отката на Go-движок** (R3).
4. **Замеры против базовой линии R0** (стенд тот же; методика 3.3) по каждому классу протокола и режиму inbound.
5. **Анти-цензурные проверки:**
   - *Отпечаток ClientHello.* Захват пакетов (Wireshark/`tshark`) реального Chrome нужной версии и профилей LAVRay → вычисление JA3, **JA4**, полный список расширений, групп, sigalgs, ALPN, GREASE-позиций. Chrome рандомизирует порядок расширений, поэтому JA3 сам по себе нестабилен: сравнивать JA4 (сортированный), множества и параметры, и распределение порядка расширений. Источник знаний: wreq сам оговаривает, что строки JA3/JA4 не воспроизводят браузер (исследование) — это ориентир осторожности.
   - *REALITY.* Взаимодействие с серверами Xray-core и sing-box (разные версии) в режимах с `flow=xtls-rprx-vision` и без; проверка поведения «шпионского» fallback к цели SNI.
   - *Поле.* Серия прогонов в сетях РФ у ≥ 3 провайдеров/режимов связи (дом, мобильный, корпоративный), по расписанию ≥ 7 суток, с теми же серверами и профилями на sing-box и Rust-движке параллельно.

**Критерии прохода ворот (численные; пороги — предложение, утверждает владелец).** Прохождение — по **каждому** протоколу отдельно: протокол переходит в R3 только если для него выполнены все пункты. Остальные остаются на sing-box.

| № | Критерий | Порог |
|---|---|---|
| G1 | Паритет функций | 100 % возможностей из матрицы, которые используются **выбранным** профилем/протоколом, поддержаны; остальное — явный откат на Go, без молчаливой деградации |

| G3 | Пропускная способность | на всех сценариях TCP/UDP ≥ 0,97 × базы R0 (внутри шума); для обоснования переноса — **хотя бы по одному** главному сценарию ≥ 1,15 × базы **или** CPU на Гбит/с ≤ 0,85 × базы |
| G4 | Задержка | p50 ≤ 1,0 × базы, p99 ≤ 0,9 × базы |

| G12 | Размер и сборка | OpenWrt aarch64/x86_64: размер ≤ 1,2 × размера Go-engine (**ДОПУЩЕНИЕ** порога); сборка воспроизводима |

**Решения по итогам ворот.**
- Все G1–G12 по протоколу пройдены → протокол в очередь R3.
- G1/G7/G8/G9/G10 не пройдены ни для одного ключевого протокола (VLESS+REALITY, Hy2, SS-2022) → **остановка**: финальное состояние — гибрид. Это допустимый и ожидаемый исход.
- Только G3–G6 не дали выигрыша → перенос data plane не оправдан производительностью; остаётся только по иным причинам (единый язык, отказ от Go-тулчейна) — вопрос владельцу.

**Риски R2.** Выигрыш может не появиться (исследование: Rust медленнее Go в shadowsocks-бенчмарке 2022; meow-rs против mihomo — «на уровне»); не существует Rust-аналога gVisor-стека; поведение sing-tun (`auto_route`, `strict_route`, kill-switch, `mixed`) придётся писать самим; REALITY-клиент у кандидатов — данные README без тестов; XHTTP закрыт у shoes только по README; серверной Rust-реализации REALITY нет (нужны Xray/sing-box серверы для стенда).

### R3. Постепенный перенос data plane

**Цель.** Два движка параллельно; Rust-движок получает профили, которые прошли G1–G12; всё остальное остаётся на sing-box; откат — в одну операцию.

**Работы.**

1. **Выбор движка на профиль.** Поле в модели профиля `engine: auto | singbox | rust` (**ДОПУЩЕНИЕ**: добавляется как необязательное поле proto — обратно-совместимо). `auto` — выбор по «карте возможностей»: каждая фича профиля сверяется с реестром поддерживаемого Rust-движком; при любой несовместимости выбирается sing-box. Реестр генерируется из матрицы R2 и версионируется.
2. **Запуск.** Супервизор запускает только тот движок, что нужен профилю. Оба бинаря поставляются; размер установщика растёт (учесть для Windows/OpenWrt, риск R-8).
3. **Поэтапный порядок включения** (по риску, наименьший вперёд; **ДОПУЩЕНИЕ**: порядок уточняется по итогам R2):
   1. прямые/простые цепочки без TUN: SOCKS/HTTP, SS-2022;
   2. VLESS/VMess/Trojan поверх WS/gRPC/TLS (без REALITY);
   3. Hy2 и TUIC (QUIC);
   4. VLESS+REALITY(+Vision) — **только после G7/G8/G9**;
   5. режим TUN — **последним** (Windows: wintun + свой стек + маршрутизация);
   6. FakeIP/DNS-правила — вместе с TUN.
4. **Режим теневого сравнения** (внутренний, для разработки): один профиль через оба движка в разное время, сравнение метрик и исходов.
5. **Телеметрия на устройстве владельца** — только локальная (без внешней отправки): счётчики откатов на sing-box и причины; пользователь должен видеть, какой движок работает (поле в `GetStatus` и UI: **ДОПУЩЕНИЕ** — минимальное, необязательное).
6. **Канареечные релизы:** сначала флаг по умолчанию `singbox`, `rust` — включается явно; затем `auto` для безопасных классов; затем по умолчанию `auto`.

**Критерии готовности R3.**
- Все профили, которые у владельца используются ежедневно (список составить в R0), работают на выбранном движке не менее 14 суток без отката по вине движка.
- Откат на sing-box проверен автотестом на каждый класс (включая переключение посреди сессии при `Stop`/`Start`, без утечки TUN и маршрутов).
- Для каждого класса «не поддерживается» есть сообщение пользователю на русском (в стиле существующих `transport_unsupported`).

**Риски R3.** Расхождение поведения DNS (кэш, порядок, fakeip) между движками даёт «странные» отказы, которых нет в тестах; двойное сопровождение конфигов (одна и та же фича в двух движках); у пользователей с `custom_config` (сырой sing-box JSON) движок всегда sing-box.

### R4. Удаление Go (только после R2/R3)

**Цель.** Отказаться от Go-тулчейна и sing-box целиком — **если** R2 и R3 прошли для **всех** используемых функций.

**Работы.**
1. Порт `common/srs` (формат `.srs`, v5): в Rust нет поддерживаемого крейта (исследование: srslist-parser — 0★, без лицензии; frsp — иной формат). Порт — по исходникам Go sing-box; тесты — на встроенных geoip cn/ru и 17 geosite из `presets/geo` (дифференциально: Go `srs.Read` → JSON, Rust → JSON, сравнить).
2. Собственный TUN-стек и вся логика `strict_route`/kill-switch (если не сделано в R3), реализация `stack: system | mixed | gvisor-эквивалент`.
3. Семантика DNS sing-box: fakeip, predefined, hosts, dns-правила с rule_set, `default_domain_resolver`, `hijack-dns`, sniff. Поверх hickory-dns либо своего резолвера; **DoH/DoQ у hickory по README не подтверждены** (исследование) — проверить.
4. `custom_outbound`/`custom_config`: либо сохранить sing-box как «внешнее ядро» (механизм `enable_external_cores` уже есть для naive/custom_external), либо отказаться от возможности — решение владельца.
5. Удалить `core/`, `NEKO_PATCHES.md`, форк sing-box из `go.mod`; перенести `updsign` на Rust (или оставить как единственный Go-инструмент CI — отдельное решение; это не часть продукта).
6. Обновить документы лицензий (`docs/LICENSES.md`), снять ограничения GPL-условия sing-box, если код не используется (оговорка об имени, раздел 7).

**Критерии готовности R4.** Нет ни одной строки Go в поставке; все 12 критериев ворот выполняются для **всех** профилей; все пользовательские сценарии, включая `custom_config`, либо работают, либо снятие поддержки утверждено владельцем и объявлено в релизных заметках. Если хотя бы один критерий не выполнен — R4 **не** выполняется (остаётся гибрид).

**Риски R4.** Самая дорогая и необратимая фаза; потеря малоизвестных функций sing-box, которыми пользуются через `custom_config`; единственный источник правды по поведению — исходники Go (нужны глубокое чтение и тесты на каждую ветку).

## 6. Инженерия производительности в Rust

Принцип: ни один пункт ниже не включается «потому что быстрее»; каждый вносится с замером на стенде R0 и выходит из репозитория, если выигрыш лежит внутри шума.

### 6.1. Control plane

- **Рантайм.** `tokio` multi-thread; число worker-потоков задаётся явно (для control plane достаточно 2–4; **ДОПУЩЕНИЕ** — по замерам), блокирующие операции (SQLite, argon2, fsync) только через `spawn_blocking` / выделенный пул; никаких блокировок мьютексом через `.await`.
- **SQLite.** Один писатель + пул читателей; подготовленные запросы с кэшем; отдельные статистики по фильтрации на стороне SQL (устраняет проблему `ListProfiles` и `GetStatus` из аудита); пагинация до сериализации; индексы по полям поиска.
- **Сериализация.** `bytes::Bytes`, сериализация proto/JSON «в буфер» без промежуточных `String`; для стримов — переиспользуемый буфер на соединение. Серверные стримы логов и соединений: ограниченные каналы с явной семантикой drop (счётчик потерь) и реальным rate-limit (в Go он не работает — аудит).
- **Логи.** Кольцо фиксированной ёмкости; постановка строк без аллокации на строку (арена/`Bytes`); обрезка до копирования (дефект `maxPendingLine` в Go).
- **Горячие вызовы UI**: `GetStatus` — 6 SQL-чтений вместо 51 (расчёт аудита; **НЕ ИЗМЕРЕНО**), `WatchConnections` — инкрементальные дельты вместо полной сортировки.

### 6.2. Data plane (только если R2 пройден)

- **Буферы.** `bytes::{Bytes, BytesMut}` и пул буферов фиксированного размера (например 16–64 КиБ) на ядро; повторное использование; отсутствие аллокаций на пакет/запись (проверяется счётчиком аллокаций, см. 6.5).
- **Копирования.** Минимизировать копии между сокетом, шифром и сокетом: шифрование «на месте» в одном буфере; `readv/writev` (на Windows — `WSASend` с несколькими буферами); для прямых соединений на Linux — `splice`/`sendfile` (для прямого TCP-прокси без шифрования; для шифруемых потоков неприменимо; **ДОПУЩЕНИЕ**: актуально в основном для OpenWrt и серверных сценариев, на Windows эффект иной — `TransmitFile` не эквивалент).
- **Крипто.** `aws-lc-rs` или `ring` (аппаратные AES-NI/PCLMUL/ARMv8 crypto, ChaCha20 с SIMD); BoringSSL (`boring`) — если нужен точный контроль ClientHello (uTLS-подобные профили; wreq/`boring2` — кандидаты исследования, **с оговорками** по сборке: cmake+perl, конфликт символов с openssl-sys). Сравнить `ring` и `aws-lc-rs` на целевом железе (x86_64 с AES-NI, ARM OpenWrt) — результат может отличаться. Для TLS-отпечатка rustls не подходит без доработок (контроль ClientHello не подтверждён — исследование).
- **Сеть.** Раздельные каналы чтения/записи; ограниченные очереди с backpressure; `TCP_NODELAY`, адаптация размеров буферов сокета; для UDP — батчинг (`recvmmsg`/`sendmmsg` на Linux, `UDP_SEGMENT`/GSO; на Windows — `WSARecvMsg`, USO/URO — **НЕ ПРОВЕРЕНО** применимость).
- **Многопоточность.** Решение между «work-stealing tokio» и «поток-на-ядро с `SO_REUSEPORT` / current_thread» принимается замером: для высокоскоростных локальных потоков второе нередко лучше (меньше синхронизации), но усложняет код. Не фиксировать до R2.
- **TUN.** Пакетный цикл без аллокаций: чтение пачки из wintun (кольцевой буфер драйвера), прямая передача в стек; на Linux — `IFF_MULTI_QUEUE`, `IFF_VNET_HDR` (GRO/GSO). Собственный стек на smoltcp (netstack-smoltcp / ipstack) — под замер: gVisor-стек в sing-box — главный претендент на «узкое место» (профиль R0 покажет). **НЕ ПРОВЕРЕНО**: быстрее ли smoltcp-стек gVisor-стека на практике.
- **Аллокатор.** `mimalloc` или `jemalloc` (не на MSVC, jemalloc под Windows ограничен — **ДОПУЩЕНИЕ**, проверить) против системного: выбор только по замерам RSS/пропускной способности/p99. Для OpenWrt/musl системный аллокатор musl заметно медленнее — выбрать явно.

### 6.3. Сборка релиза

- `[profile.release]`: `lto = "fat"`, `codegen-units = 1`, `panic = "abort"` (где допустимо; в control plane `panic = "unwind"` + перехват ради целостности БД — решить), `opt-level = 3` (для OpenWrt вариант `s`/`z` по размеру), `strip = "symbols"`.
- **PGO** (profile-guided optimization) по сценариям стенда R0 (+ BOLT на Linux, если окупится): PGO-сборка допустима только если она **воспроизводима** (профили хранятся в репозитории с хэшем; в CI есть шаг пересборки).
- `target-cpu`: общий билд без `native` (пользователи с разными CPU); мультиверсионные функции (`#[target_feature]` + runtime-детект) для AES/ChaCha/memchr.
- Аудит отмечает: для оболочки thin LTO + CGU1 дал −5,70 % размера, **runtime-эффект не измерен** — то же правило.

### 6.4. Профилирование

`perf` + flamegraph (Linux/OpenWrt-класс), ETW/WPR + WPA (Windows), `tokio-console` для задержек задач, `tracy` для покадрового профиля горячих циклов, `dhat`/`heaptrack` для аллокаций, `cargo-llvm-cov` для покрытия. Для сравнения с Go — pprof sing-box (R0).

### 6.5. Бенчмарки и ворота в CI

- `criterion` — микробенчмарки парсеров, кодеков, крипто, сериализации; допуск регрессии (например > 5 % → fail) на выделенной машине (не на общем CI-раннере — шум).
- `iai-callgrind` (число инструкций, стабилен на общем CI) — там, где Linux; под Windows — только criterion.
- **Allocation gates**: тесты со счётчиком аллокаций (`stats_alloc`, `dhat` в тестовом режиме) на горячих путях: «0 аллокаций на пакет в установившемся режиме» — как утверждение, проверяемое тестом, а не как слова.
- Макробенчмарки (стенд R0) — по расписанию (nightly) на выделенной машине владельца; результаты — таблицей в `docs/rust-migration/bench/`.
- Фаззинг: `cargo-fuzz` (libFuzzer) на парсеры, декодеры протоколов, форматы файлов — в nightly.

**Ничего из этого раздела не обещает числового выигрыша.** Это набор инструментов и ограничение: чего не измерено — того не заявляем.

Формулировку документа лицензий обновить (`docs/LICENSES.md`).
- Порт `.srs`: формат — публичная спецификация docs; код порта писать **по спецификации и тестам**, а не копировать исходники Go (иначе GPL-производная; допустимо под GPL-3.0, но фиксируется в заголовках файлов и NOTICE).
- Процесс: включить `cargo-deny` (allow-list лицензий) и `cargo-about` в CI; генерация NOTICE при каждом релизе.

## 9. Трудоёмкость

**Единица — агенто-неделя** (**ДОПУЩЕНИЕ**): одна неделя работы одного ИИ-агента при участии владельца для решений и приёмки, включая написание кода, тестов и самопроверку, плюс независимое ревью. Эквивалент человеко-неделям здесь не выводится.

Допущения расчёта:
- пропускная способность агента — порядка 2–4 тыс. строк проверенного кода и тестов в неделю (**ДОПУЩЕНИЕ**; зависит от плотности сложности: парсеры дешевле, крипто и сеть дороже);
- Go prod-код к переносу около 45 тыс. строк (без `internal/gen`, без sing-box) и около 46,5 тыс. строк тестов; Rust обычно не короче Go на тех же функциях (**ДОПУЩЕНИЕ**);
- стоимость ревью и исправлений заложена в диапазон;
- время владельца на решения и стенд — отдельно, в этих цифрах не учтено;
- диапазоны широки намеренно; уточнять после R0 и первого спайка Connect-слоя.

| Фаза | Диапазон, агенто-недель | Основные составляющие | Что параллелится |
|---|---|---|---|
| R0 | 3–5 | выгрузка корпусов и golden, харнесс, стенд, профилирование | выгрузка корпусов ‖ стенд замеров |
| R1 | 35–60 | `api` (самый большой, 14 тыс. + тесты) 10–16; `store`+`nekoimport`+`backup` 6–10; `updates` 6–10; `cfgbuild` 4–7; `subs`+`links`+`presets`+`model` 5–9; `mcp`+`web`+`gateway`+`headless`+`cmd` 5–10; внутренний API движка, супервизор, фасад 3–6 | пункты 1–5 списка 4.1.2 независимы после `model`; `api` по сервисам; `updates` и `web` отдельными потоками |
| R2 | 12–25 | прототип движка (подмножество) 6–12; матрица совместимости и interop 3–6; замеры и профилирование 2–4; анти-цензурные проверки (включая поле 7+ суток календарно) 1–3 | R2 начинается раньше конца R1 (не зависит от Rust-API кроме `engine.proto`) |
| R3 | 20–45 | протоколы по классам 8–20; TUN (Windows) 6–15; DNS/FakeIP 3–7; выбор движка, откаты, UI-статус 3–5 | классы протоколов параллельны; TUN — отдельный поток |
| R4 | 10–20 | порт `.srs` 2–3; остаточный TUN-стек и DNS-семантика 4–8; `custom_config`-решение 1–3; чистка Go, лицензии, документы 2–4 | порт `.srs` параллелен остальному |

**Итог.** При последовательной работе один агентский поток даёт сумму: нижняя граница около 80, верхняя около 155 агенто-недель; при трёх параллельных потоках и непрерывном ревью календарная длительность может уложиться примерно в 8–14 месяцев (нижняя граница достижима только без провалов ворот R2). Если после R2 выбирается гибрид, объём составит только R0+R1 (≈ 38–65 агенто-недель) плюс ограниченные вложения в R2 (≈ 12–25) — **это основной ожидаемый сценарий для планирования бюджета.**

Календарные сроки зависят от: доступности второго ПК и тестовых серверов, времени владельца на решения, длительности полевых замеров (7+ суток на цикл).

## 10. Что можно делать параллельно

- R0 (корпуса) ‖ R0 (стенд) ‖ исправление Go-узких мест control plane.
- R1: после `model` независимо идут `links`, `subs`, `presets`, `backup`; затем `cfgbuild`; `updates` — отдельный поток (безопасность, свои ревьюеры).
- R2 (прототип движка) не ждёт конца R1: достаточно `engine.proto` и `cfgbuild`.
- R2: протоколы — параллельно (SS, VLESS, Hy2, TUIC — независимые прототипы); TUN — отдельный поток.
- R3: классы протоколов включаются независимо; общий критерий — отсутствие отката по вине движка.
- Нельзя параллелить: схему БД (один владелец), proto-контракт (заморожен), порядок включения REALITY и TUN (после ворот).

## 11. Первые конкретные шаги

### Ближайший PR (неделя 1)

1. **`docs/rust-migration/` и `conformance/`**: каталог для нейтральных корпусов и golden; скрипт выгрузки из Go-тестов (чтение `cfgbuild/testdata/golden`, `links/testdata`, фаззинг-корпуса `testdata/fuzz/*`); никаких изменений в логике ядра.
2. **Workspace `lavray/rust/`** (или `lavray/core-rs/`): пустые крейты `lavray-model`, `lavray-links`, `lavray-cfgbuild`, `lavray-proc`; CI: `cargo fmt`, `clippy -D warnings`, `cargo-deny` (лицензии), `cargo-audit`. **Отдельный** от `shell/` Cargo-проект, чтобы не трогать сборку Tauri; общий код процессов (`coreproc`) вынести позже.
3. **Спайк «Connect JSON на Rust»** (1 неделя): минимальный сервер с двумя RPC (unary `CoreService.GetStatus`-подобный и server-streaming `SubscribeEvents`-подобный) на `connectrpc`, затем на самописном hyper-слое; тест — реальный `connect-web` клиент из `ui/src/lib/core.ts`; замер p50/p99 против Go. Результат решает вопрос R-3.
4. **Спайк «внутренний API движка»**: минимальный `lavray-engine` (Go) с `Start(config_json)`/`Stop`/`StreamLogs` поверх существующего `inst.SingBoxRunner` и Rust-супервизор с готовым кодом из `shell/src/coreproc` (проверка, что вынос в `lavray-proc` реален).
5. **`buf breaking`** в CI для `proto/lavray.proto`.
6. **Заготовка стенда**: сценарий iperf3 + сбор CPU/RSS на одном ПК (loopback) — как отладка методики; боевые цифры — после появления второго узла.

### Рядом с этим (недели 2–5)

- Профилирование текущего sing-box и публикация базовой линии (R0).
- Первая пара модулей Rust (`model`, `links`) с дифференциальными тестами — чтобы получить реальную скорость переноса и перекалибровать оценки раздела 9.
- Решение по исправлению оставшихся Go-узких мест (`ListProfiles`, `WatchConnections`) — до или вместо переноса.

### Что нужно от владельца

1. **Решение по цели.** Принять формулировку: основной ожидаемый результат — Rust control plane (R1); data plane переносится **только** при прохождении ворот R2. Подтвердить пороги G1–G12 или изменить.
2. **Контракт ошибок batch** и другие изменения поведения (аудит п.2, 6) — принимать ли.
3. **Второй ПК** (или VPS) для двухузлового стенда; доступ в сеть с высокой пропускной способностью (≥ 1 Гбит/с) без шумных соседей. Без этого решения по data plane не принимаются.
4. **Тестовые серверы:** sing-box и Xray (разные версии) с каждым протоколом LAVRay, включая REALITY с реальной «целью» SNI; домен(ы) и сертификаты.
5. **Сети для полевых тестов в РФ:** ≥ 3 провайдера/режима связи; согласие на 7+ суточные прогоны.
6. **Роутер OpenWrt** (aarch64 или x86_64) для тестирования gateway/headless и размера бинаря.
7. **Список ежедневных профилей** (в обезличенном виде: протокол, транспорт, TLS/REALITY, режим TUN) — критерий готовности R3.
8. **Решение по `custom_config`/`custom_outbound`** (сырой sing-box JSON): сохранить через внешний sing-box или отказаться (нужно к R4).
9. **Бюджет на внешний аудит безопасности** крипто-частей (по желанию).
10. **Исключения антивируса/Defender** для стенда на время замеров, чтобы шум не превышал эффект.

## 12. Что осталось неясным (сводка допущений и непроверенного)

- Реальный выигрыш data plane от Rust — **неизвестен**; единственные публичные цифры относятся к другим системам (mihomo, shadowsocks), см. исследование.
- Пригодность `connectrpc` (pre-1.0) для JSON-протокола Connect и server-streaming — не проверена; запасной путь описан.
- Выбор крейтов для SQLite, YAML, TUF-lite, argon2, MCP — в исследовании не оценивался.
- Форк sing-box (`35f3fd0`, версия `1.14.1-neko.1`) относительно upstream v1.14.4 не сравнивался; объём патчей (`NEKO_PATCHES.md`) на перенос не оценивался.
- Эквивалентность поведения sing-tun (Windows `auto_route`, `strict_route`) и возможность её воспроизвести на Wintun без драйверных ухищрений — не проверена.
- Возможность вынести `shell/src/coreproc` в общий крейт без изменения поведения оболочки — не проверена.
- Права/повышение привилегий для движка при TUN (в ядре есть `elevation_windows.go`) — взаимодействие с двухпроцессной схемой требует отдельной проверки.
- Все числовые пороги ворот и оценки трудоёмкости — предложения, а не измерения.
