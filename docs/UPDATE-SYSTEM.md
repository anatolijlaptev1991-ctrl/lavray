# LAVRay Update System — спецификация v2.0

Переработана по аудиту 2026-10 (`docs/AUDIT-CLAUDE-2026-10.md` §2.4, сырой отчёт `docs/audit-2026-10/raw/03` §3): v1.0 подписывала только артефакт, держала один ключ и один аккаунт, не пережила бы блокировку GitHub и переход OpenWrt 25.12 на apk. Историю изменений v1.0 см. в git; отличия перечислены в §11.

## 1. Принципы

1. **Никогда не ломать работающий туннель**: обновление применяется только по явному действию пользователя или в спокойном состоянии (не в момент активной сессии, если не подтверждено).
2. **Целостность обязательна**: артефакт без валидной подписи и чексуммы не применяется никогда. Ошибка проверки = безопасный отказ + уведомление.
3. **Откат всегда возможен** — и выполняет его **старая версия**: предыдущая версия сохраняется; маленький rollback-помощник (или служба) ждёт heartbeat новой и откатывает сам, если новая не стартует.
4. **Прозрачность**: пользователь видит, что обновится (приложение / ядро / пресеты / geo-данные), changelog на своём языке, источник-репозиторий.
5. **Каналы**: `stable` (по умолчанию) и `beta`. Смена канала — явное действие.
6. **Доверие даёт подпись, а не хост**: хранилища взаимозаменяемы; allowlist источников берётся из подписанного `sources.json`, а не из кода.
7. **Молчание ≠ нет обновлений**: «проверка не удалась» и «обновлений нет» — разные состояния; клиент показывает «последняя успешная проверка N дней назад».
8. **Обновление переживает блокировки**: сначала через активный туннель, затем напрямую; зеркала на разных провайдерах; офлайн-путь «Установить из файла».

## 2. Модель угроз

| Угроза | Мера |
|---|---|
| Компрометация аккаунта GitHub / CI | Ключи подписи — вне CI и вне аккаунта (§4); подпись релиза — вне CI или в защищённом Environment с ревью; зеркала вне GitHub (`sources.json`); immutable releases |
| Кража ключа подписи | Офлайн root-ключи на аппаратных токенах, threshold 2-из-3; онлайн-ключи со сроком `expires`; отзыв ключа — новая версия `root.json`; процедура аварийной ротации в `docs/SECURITY.md` |
| Freeze (вечный старый манифест) | `timestamp.json` со сроком ≤ 7 дней; клиент предупреждает после 7 дней без успешной проверки, красный статус после 30 |
| Откат на старую подписанную версию (downgrade) | Монотонный `serial` манифеста по каждому каналу; клиент хранит максимум и отвергает меньший |
| Mix-and-match (сборка обновления из кусков разных релизов) | Все артефакты и их sha256 — в одном подписанном манифесте; сборка не применяется при несовпадении любой части |
| Подмена канала (beta вместо stable, `mandatory:true` как DoS) | `product`, `channel` и `mandatory` — внутри подписанного `manifest.json`; клиент отвергает чужой `product`/`channel` |
| Подмена/повтор манифеста (replay) | `serial` + `expires` + подпись trusted comment `product;platform;channel;version;serial` в minisign |
| MITM и DNS-подмена | HTTPS-only; DNS — через DoH ядра; проверка подписи и хеша — после загрузки, на каждом источнике и редиректе |
| Блокировка GitHub (РФ/КНР) | Подписанный `sources.json`: зеркала GitLab/Codeberg, два своих домена на разных провайдерах и регистраторах; jsDelivr — только для метаданных; обновление через туннель |
| Частичная загрузка / обрыв | Контроль `Content-Length`, sha256, докачка (Range) или повтор; обрывки удаляются; копия в защищённый каталог и повторная проверка перед запуском (анти-TOCTOU) |
| Подмена пресетов и geo (тихий обход туннеля) | Пресеты и geo подписываются тем же механизмом и идут с `serial` (§8) |

## 3. Метаданные (TUF-lite)

Четыре подписанных документа. Формат: `{"signed": {…}, "signatures": [{keyid, sig}…]}`.

### 3.1 `root.json` — корень доверия (офлайн)

```json
{"signed":{"type":"root","version":1,"expires":"2027-10-01T00:00:00Z",
  "keys":{"k1":{"alg":"ed25519","pub":"<base64>"},"k2":{"alg":"ed25519","pub":"<base64>"},"k3":{"alg":"ed25519","pub":"<base64>"},
          "t1":{"alg":"ed25519","pub":"<base64>"},"r1":{"alg":"ed25519","pub":"<base64>"}},
  "roles":{"root":{"keyids":["k1","k2","k3"],"threshold":2},"timestamp":{"keyids":["t1"],"threshold":1},
           "manifest":{"keyids":["r1"],"threshold":1},"sources":{"keyids":["r1"],"threshold":1}}},
 "signatures":[{"keyid":"k1","sig":"<base64>"},{"keyid":"k2","sig":"<base64>"}]}
```

> **Фаза 1 (решение владельца 2026-10-23):** `keys` содержит один root-ключ k1, `roles.root = {"keyids":["k1"],"threshold":1}`. Пример выше — целевое состояние 2-из-3; переход без смены формата, версией `root.json` N+1 (процедура — `docs/SECURITY.md` §4.1).

### 3.2 `timestamp.json` — свежесть (онлайн, перевыпускается при каждом релизе)

```json
{"signed":{"type":"timestamp","version":1207,"expires":"<now+7d>",
  "meta":{"manifest-stable.json":{"serial":42,"sha256":"<hex>","length":2817},"manifest-beta.json":{"serial":57,"sha256":"<hex>","length":2903}}},
 "signatures":[{"keyid":"t1","sig":"<base64>"}]}
```

### 3.3 `manifest.json` — содержимое релиза (по одному на продукт × канал)

```json
{"signed":{"type":"manifest","product":"lavray-windows","channel":"stable","serial":42,"expires":"<now+30d>",
  "app":{"version":"1.2.0","minUpgradeFrom":"1.0.0","assets":{"windows-x64":{"path":"v1.2.0/LAVRay-1.2.0-x64-setup.exe","sha256":"<hex>","length":12345678,"minisig":"<minisign>"}}},
  "core":{"version":"1.14.1-lav.1","minApp":"1.2.0"},
  "presets":{"lav-ru":{"rev":43,"path":"presets/lav-ru-43.json","sha256":"<hex>"},"lav-cn":{"rev":5,"path":"presets/lav-cn-5.json","sha256":"<hex>"}},
  "geo":{"path":"geo/2026-10-20.zip","sha256":"<hex>","length":3456789,"generatedAt":"2026-10-20"},
  "notes":{"ru":"…","zh":"…","en":"…","es":"…","de":"…"},"mandatory":false},
 "signatures":[{"keyid":"r1","sig":"<base64>"}]}
```

### 3.4 `sources.json` — источники (меняются редко)

```json
{"signed":{"type":"sources","version":3,"expires":"<now+180d>",
  "artifacts":["https://github.com/<org>/lavray-windows/releases/download/","https://codeberg.org/<org>/lavray-windows/releases/download/",
               "https://updates-a.<domain>/lavray-windows/","https://updates-b.<other-domain>/lavray-windows/"],
  "metadata":["https://<org>.github.io/lavray-windows/meta/","https://cdn.jsdelivr.net/gh/<org>/lavray-windows@meta/","https://updates-a.<domain>/meta/"]},
 "signatures":[{"keyid":"r1","sig":"<base64>"}]}
```

**Правила.** Клиент хранит последний `root.version`, максимальный `serial` по каждому каналу и `expires`; отвергает меньший `serial`, чужой `product` или `channel`, истёкший `timestamp`. Ротация root — новый `root.json`, подписанный порогом старых ключей; отзыв ключа — удаление из `keys` в новой версии root. Trusted comment minisign артефакта: `product;platform;channel;version;serial`.

## 4. Ключи и CI

- Фаза 1 (решение владельца 2026-10-23): один офлайн root-ключ у владельца (threshold 1); цель — офлайн root-ключи у 2–3 человек на аппаратных токенах (threshold 2-из-3). Онлайн-ключи `timestamp` и `manifest` — со сроком действия.
- Подпись релиза — вне CI (подписывающий монтаж на машине релиз-инженера) или в защищённом GitHub Environment с обязательным ревью; аппаратная 2FA на аккаунтах; защищённые теги.
- `permissions: read` по умолчанию во всех workflow; actions пинируются по SHA; никаких `ACTIONS_ALLOW_UNSECURE_COMMANDS`; загрузки в CI — только с проверкой хеша.
- Immutable releases (перепубликация артефакта запрещена), provenance-аттестация, SBOM.
- Воспроизводимая сборка: `-trimpath`, `SOURCE_DATE_EPOCH`, стабильные флаги — пользователи и зеркала могут сверить сборку.
- Процедура аварийной ротации ключей — в `docs/SECURITY.md`.

## 5. Алгоритм клиента

1. `timestamp.json` качается **параллельно минимум из двух** источников метаданных (connect 3 с, первый байт 5 с); берётся наибольший валидный.
2. Проверка цепочки: root → timestamp → manifest (подписи, `serial`, `expires`, `product`, `channel`).
3. Артефакт — с любого источника из `sources.json`, с докачкой; проверка длины, sha256, minisign.
4. Копия в защищённый каталог и **повторная проверка перед запуском** (анти-TOCTOU: проверили в `%TEMP%` — запускать оттуда же нельзя).
5. Порядок сети: сначала через активный туннель, затем напрямую; DNS — через DoH ядра.
6. Последний рабочий источник запоминается и пробуется первым.
7. Состояние «последняя успешная проверка N дней назад»: предупреждение после 7 дней, красный статус после 30; до первой успешной проверки текст «нет обновлений» не показывается.
8. Офлайн-путь «Установить из файла»: инсталлятор + `.minisig` + манифест; проверяется той же цепочкой.

Периодичность — не чаще раза в 6 ч, со случайным джиттером, без идентификаторов, через туннель, если он поднят (приватность: запрос не должен палить LAVRay провайдеру).

## 6. Установка и откат по платформам

- **Windows.** Per-machine NSIS; службы нет — TUN работает, когда приложение запущено от администратора (автозапуск с правами из установленной копии — задача планировщика `LAVRay-<SID>`). Выпускается только NSIS (у MSI нет хука, цель убрана из `bundle.targets`). Хук NSIS `NSIS_HOOK_POSTUNINSTALL` (`shell/windows/hooks.nsh`) при удалении (не при обновлении) убирает автозапуск: значение `HKCU\...\Run` и все задачи `LAVRay*`; остановка сайдкара и снятие TUN/системного прокси [проверь API Tauri для хуков]. Прошлый инсталлятор хранится локально; откат выполняет маленький rollback-помощник старой версии (или служба) по отсутствию heartbeat новой после перезапуска.
- **macOS.** Только из каталога «Программы» (иначе App Translocation заблокирует самообновление — требовать «Переместить в Программы» до включения апдейтера). Developer ID + notarization обязательны до публичного релиза; привилегированный помощник — SMAppService.
- **Linux.** AppImage — встроенный updater, но без TUN либо с systemd-помощником. `.deb` — apt-репозиторий с `signed-by` и `Valid-Until`; обновление строго `apt-get install --only-upgrade lavray` (не общий `apt upgrade`); пул пакетов на Releases/CDN, индекс на Pages (лимит Pages ~1 ГБ).
- **OpenWrt.** **Два фида**: ipk + usign (24.10) и apk + подпись (25.12+); имена пакетов `lavrayd`, `luci-app-lavray`, `lavray-webui` — одинаковые во всех документах. Ключ фида кладётся в `/etc/opkg/keys/` или `/etc/apk/keys/` **до** первого обновления (отпечаток публикуется вне GitHub — сайт/README/Telegram). Скрипт `lavray-update` определяет менеджер, выбирает рабочее зеркало и переписывает единственный активный URL фида. Прошлый пакет хранится локально. Watchdog procd: «нет связи N минут после обновления → откат на прошлый пакет». Обновляются только именованные пакеты LAVRay (не весь мир). Статус и логи — в tmpfs; geo — не чаще раза в неделю; отказ при свободном месте < 2× размера пакета. Подробности шлюза — `docs/OPENWRT-GATEWAY.md`.

## 7. Ядро

Отдельная доставка ядра **разрешена** по тому же манифесту с полем `minApp` (быстрый ответ на CVE ядра и блокировки протоколов; в v1.0 было запрещено). Версия ядра — своя схема (`1.14.1-lav.N`), не semver-сравнение с upstream (по semver `1.14.1-lav.1` < `1.14.1` — сравнение только своей схемой). Обновление ядра требует версию приложения ≥ `minApp`. Политика переноса neko-патчей и гейты обновления upstream — без изменений (см. историю v1.0 §6: аудит changelog → лицензия upstream → патчи → L1/L2 → smoke → рекурсия до нуля → тег `core-<version>`); при каждом обновлении явно проверяется условие `sing-box/LICENSE`:16 об имени.

## 8. Пресеты и geo

Подписываются тем же механизмом (секции `presets` и `geo` манифеста, `serial`/`rev` и sha256). Обновление пресета, у которого есть пользовательские правки, — только через diff/merge, никогда молча. Встроенные наборы `.srs` для пресетов — в поставке (старт без сети, FR-UI-266).

## 9. Каналы

Переход stable → beta — с подтверждением (предупреждение о стабильности). Переход beta → stable — ожидание, пока stable догонит номер версии, либо явный даунгрейд с бэкапом данных (клиент не должен застревать на beta).

## 10. Тесты (обязательный CI-гейт)

Позитив/негатив подписи; просроченный `timestamp`; меньший `serial`; чужой канал/product; недоступный GitHub при доступном зеркале; частичная загрузка; подмена на редиректе; занятые файлы сайдкара; неработающая новая версия → откат; opkg и apk в контейнерах SDK; zip-slip и симлинки в архивах; офлайн-установка из файла; downgrade-артефакт (старый, но валидно подписанный) отвергается.

## 11. Отличия от v1.0 (кратко)

| Было (v1.0) | Стало (v2.0) |
|---|---|
| Подписан только артефакт (Tauri Updater) | TUF-lite: root/timestamp/manifest/sources, serial, expires |
| Один ключ, ротация «с major-версией» | Офлайн root 2-из-3 + онлайн-ключи со сроком; отзыв; SECURITY.md |
| Пиннинг github.com | Доверие подписи; подписанный список зеркал; через туннель |
| `latest.json` без защиты метаданных | `manifest.json` с `product`/`channel`/`serial`/`mandatory` внутри подписи |
| Ядро только в связке с приложением | Отдельная доставка с `minApp` |
| Откат «исполняет новая версия» | Rollback-помощник старой версии + heartbeat |
| OpenWrt — только opkg | Два фида: ipk/usign (≤24.10) и apk/подпись (≥25.12) |
| «Нет сети → нет обновлений» | Статус последней успешной проверки + зеркала + офлайн-файл |
> **Статус реализации (0.5.0, T-75).** Клиент подключён к ядру и оболочке: проверка, загрузка с докачкой и minisign, повторная проверка перед установкой, установка NSIS (`/S`, один UAC), откат прошлым установщиком и экран «Обновления». Сборка без вшитого корня доверия честно отвечает «обновления не настроены» (§12.1). Доверенный корневой ключ один (порог 1), «2-из-3» — следующая фаза (§3.1). Детали реализации, церемония ключей и поведение NSIS — §12.

## 12. Реализация T-75 (0.5.0): эксплуатация

### 12.1 Состояние «обновления не настроены»

В репозитории лежит заглушка `core/cmd/lavray-core/root.json` (JSON без поля `signed`). Пока владелец не положил туда настоящий корень, ядро отвечает на `CheckUpdates` ошибкой FAILED_PRECONDITION с причиной `not_configured` («updates not configured (no trust root in this build)»), а экран «Обновления» показывает это прямо. Молча говорить «обновлений нет» нельзя: проверка, которой не было, не равна проверке без новостей. Причина идёт в начале сообщения (`not_configured: …`) и в заголовке `Lavray-Update-Reason`.

Настоящий корень подставляется одним из способов (флаг сильнее файла):

```
# файлом: заменить core/cmd/lavray-core/root.json подписанным root.json
# флагом компоновщика:
go build -ldflags "-X main.rootJSONB64=$(base64 -w0 root.json)" ./cmd/lavray-core
# адреса bootstrap-источников метаданных (по умолчанию GitHub Pages и jsDelivr):
go build -ldflags "-X main.bootstrapURLs=https://a.example/meta,https://b.example/meta" ./cmd/lavray-core
```

Версия приложения берётся из `internal/version` (`-X …/internal/version.Version=<версия>`), как у всех остальных частей ядра.

### 12.2 Роли и ключи

| Ключ | Роль | Где хранится | Формат в `root.json` |
|---|---|---|---|
| k1 | `root` | офлайн у владельца (две зашифрованные USB и бумажная копия), порог 1 | `{"alg":"ed25519","pub":"<base64, 32 байта>"}` |
| t1 | `timestamp` | Environment `release-signing`, секрет `LAVRAY_TIMESTAMP_KEY` | ed25519 |
| r1 | `manifest`, `sources` | там же, `LAVRAY_MANIFEST_KEY` | ed25519 |
| a1 | `artifact` | там же, `LAVRAY_ARTIFACT_KEY` | `{"alg":"minisign","pub":"<base64 файла .pub: Ed + keyid + ключ, 42 байта>"}` |

Роль `artifact` обязательна: без неё клиент отказывает (fail-closed, причина `artifact_role_missing`). Ключ метаданных не может подписать установщик и наоборот: тип ключа проверяется при разборе корня.

### 12.3 Файлы на источнике

```
root.json            текущий корень          2.root.json, 3.root.json …  цепочка ротации
sources.json         список зеркал (r1)      timestamp.json              свежесть, не больше 7 суток (t1)
manifest-stable.json manifest-beta.json      (r1; sha256 и длину пиннит timestamp)
v<версия>/LAVRay-<версия>-x64-setup.exe      установщик (+ .minisig в релизе)
```

Клиент: ротация корня `N → N+1` до 404 (не больше 64 шагов; срок проверяется у итогового корня, поэтому просроченный вшитый корень с валидным преемником работает) → `sources.json` → `timestamp.json` параллельно со всех источников (побеждает наибольшая версия; версия ниже сохранённой — откат метаданных) → манифест канала → решение по **версии приложения** (`CompareVersions > 0` и `minUpgradeFrom`), а не по serial. Serial защищает только от отката метаданных. Принятые корни хранятся ЦЕПОЧКОЙ файлов `<данные>/updates/roots/N.root.json` и при каждой загрузке перепроверяются от вшитого корня (порог ключей предыдущего корня и подпись новыми): подложенный в каталог самоподписанный «корень v7» в цепочку не встаёт. Конец цепочки (`N+1` нет) объявляется, только когда КАЖДЫЙ источник ответил «нет файла»; молчащий, зависший или упавший источник даёт ошибку «проверка не удалась» (UNAVAILABLE), а не тихий конец ротации. Это осознанный fail-closed: молчащее зеркало могло бы скрывать новый корень (отзыв ключа). Ошибка называет зеркало: сообщение `mirror_unreachable: <хост>[, <хост>]` и заголовок `Lavray-Update-Reason: mirror_unreachable`; интерфейс показывает «не удалось связаться с зеркалом обновлений», имя зеркала и совет подключиться к VPN и повторить — проверка идёт сначала через туннель, а зеркало (например, jsDelivr) бывает недоступно только напрямую. Цена решения: одно мёртвое зеркало из bootstrap-списка останавливает проверки, пока оно не вернётся или не будет убрано из `sources.draft.json` новым релизом.

### 12.4 Церемония ключей (на машине без сети; один раз до первого выпуска)

Выполняет владелец. Приватные ключи в репозиторий и в CI-секреты, кроме t1/r1/a1, не попадают; утилита отказывается писать и читать ключ внутри git-дерева.

1. Сгенерировать четыре ключа (из `core/`, каталог вне репозитория):
   ```
   go run ./cmd/updsign genkey -role root      -out D:/keys/k1.sec -pub D:/keys/k1.pub.json
   go run ./cmd/updsign genkey -role timestamp -out D:/keys/t1.sec -pub D:/keys/t1.pub.json
   go run ./cmd/updsign genkey -role manifest  -out D:/keys/r1.sec -pub D:/keys/r1.pub.json
   go run ./cmd/updsign genkey -role artifact  -out D:/keys/a1.sec -pub D:/keys/a1.pub.json
   ```
2. Собрать черновик `root-draft.json` (`type: root`, `version: 1`, `expires` через 2 года, `keys` {k1, t1, r1, a1} из поля `root_key` публичных файлов, `roles` {root→k1, timestamp→t1, manifest→r1, sources→r1, artifact→a1}, порог 1) и подписать root v1:
   ```
   go run ./cmd/updsign root -key k1=file:D:/keys/k1.sec -in root-draft.json -out root.json
   ```
3. Прислать публичный `root.json` (его можно коммитить) и положить в `core/cmd/lavray-core/root.json`.
4. k1 записать на две зашифрованные USB и на бумагу; с рабочей машины удалить.
5. Секреты t1, r1, a1 (содержимое файлов `.sec`) положить в Environment `release-signing` как `LAVRAY_TIMESTAMP_KEY`, `LAVRAY_MANIFEST_KEY`, `LAVRAY_ARTIFACT_KEY`; ревьюер Environment — владелец; секрет t1 дополнительно кладётся в Environment `release-timestamp` (§12.5а).
6. Включить GitHub Pages (ветка `gh-pages`) и защиту тегов `v*`. Environment `release-signing` (ключи t1, r1, a1, ревьюер — владелец) ограничить **тегами `v*`** (Settings → Environments → Deployment branches and tags → Selected branches and tags → Tag `v*`): иначе любая ветка с правом на workflow получит ключи. Отдельный Environment `release-timestamp` содержит ТОЛЬКО t1, разрешён только для ветки по умолчанию и без ревьюера (ночное задание `meta-refresh`).
7. Выбрать второе зеркало артефактов (Codeberg или свой домен) и добавить его в `scripts/release/sources.draft.json`.

Срок корня — 2 года; `TestEmbeddedRootValid` требует запас больше 180 дней и сообщает, когда пора выпускать новый. Ротация корня: новый `root` версии N+1 подписывается ключами прежнего корня **и** новыми (`updsign root -key k1=… -key k2=… -prev root.json -in … -out N+1.root.json`), кладётся как `N+1.root.json` и `root.json`.

### 12.5 Выпуск в CI

Джоб `sign` (`release-windows.yml`) работает в Environment `release-signing`. Без секретов все шаги пропускаются, джоб завершается успешно, релиз выходит без `meta/`. С секретами: собирает `updsign`, берёт текущий `meta/` из `gh-pages`, подписывает манифест канала (канал `beta`, если в версии есть `-`), `sources.json`, `timestamp.json` и `.minisig` установщика, **до публикации** запускает `updsign verify` (тем же кодом, что и клиент, с проверкой установщика), затем пушит `meta/` в `gh-pages` и прикладывает `.minisig` к релизу. Второй источник метаданных — jsDelivr (`cdn.jsdelivr.net/gh/…@gh-pages/meta`).

### 12.5а Кто продлевает свежесть (отступление от спецификации §3.2/§4)

Спецификация v2.0 не называла исполнителя: timestamp живёт 7 суток, а подписывается только при теге. Принято:

- `meta-refresh.yml` — ежедневный cron (и ручной запуск) в Environment `release-timestamp` (только t1, только ветка `main`: `if: github.ref == 'refs/heads/main'`, потому что в событии `schedule` имя ветки по умолчанию из контекста бывает пустым; без ревьюера): переподписывает **только** `timestamp.json` и публикует в `gh-pages`. Ключи r1 и a1 ему недоступны. Порядок шагов: подпись timestamp → `updsign verify -role timestamp` (корни, подпись, срок, пины манифестов; сами манифесты не проверяются) → **публикация** → проверка каждого канала → предупреждение о сроке. Просроченный манифест одного канала краснит задание, но свежий timestamp уже опубликован.
- Манифест и `sources.json` живут **90 суток** (по спецификации было 30): их подпись требует ревью, и 30 суток заставляли бы выпускать релиз раз в месяц. Задание `meta-refresh` последним шагом падает за 14 суток до истечения (`updsign expiry -within 336h`) с сообщением: выпустите релиз или запустите ручной `meta-resign`.
- `meta-resign.yml` — ручной запуск на теге `v*` в Environment `release-signing` (с ревьюером): `updsign resign` меняет только `expires` манифестов и sources (версия, активы и подписи minisign остаются) и перевыпускает timestamp.
- `updsign verify -channel X` проверяет только выпускаемый канал: просроченный beta не блокирует stable. Версия, не новее опубликованной в канале, не подписывается (`updsign manifest -published-dir`).
- Часы клиента могут отставать до 24 часов (допуск окна свежести timestamp); дальше причина `clock_skew` («проверьте дату и время»), а не «просрочено».

### 12.5б Ввод workflow

Ввод ручного запуска (`days` у `meta-resign`) недоверенный: арифметика bash над строкой исполняет `a[$(cmd)]`. Поэтому он проверяется отдельным заданием `validate` БЕЗ секретов и без Environment (`^[0-9]{1,4}$`, 1–365 суток) и передаётся дальше только готовым числом часов; `${{ inputs.* }}` и `github.event.*` внутри `run:` запрещены тестом `scripts/tests/test_signing_workflows.py`.

### 12.6 Установка и откат (оболочка)

- Ядро скачивает установщик в `<данные>/updates/staging/<sha256>-<имя>` (`.part`, Range, точная длина, sha256, minisign), шлёт `verified{staged_path, sha256}`; `ApplyUpdates(APP)` ещё раз проверяет файл на диске и отвечает `ready_for_restart`.
- Оболочка (`update_apply`) НЕ верит странице: sha256 и версия от неё — лишь подсказки. Она проверяет путь, открывает файл с запретом записи (`FILE_SHARE_READ`, без перехода по ссылкам, с проверкой `GetFinalPathNameByHandleW`), считает sha256 по дескриптору и, пока дескриптор удерживается, запускает **встроенное ядро** из каталога установки (с вшитым хэшем, не из staging и не из каталога данных): `lavray-core verify-artifact --file F --sig F.minisig --data <данные>`. Подпись проверяется ключом роли `artifact` из цепочки корней от вшитого, плюс trusted comment (продукт, платформа), плюс версия новее установленной. Установщик запускается, только если код выхода 0, сумма из ответа ядра равна сумме оболочки и версия — ожидаемая (`signature_invalid`, `version_mismatch`, `sha256_mismatch`, `core_unavailable` — отказы без запроса UAC). Затем оболочка останавливает ядро, снимает системный прокси и запускает установщик с `/S` через `ShellExecuteExW` с `runas` и рабочим каталогом `%SystemRoot%\System32` (отказ UAC, код 1223, — `uac_cancelled`, установщик не запущен). Замок «установка идёт» остаётся занятым до выхода приложения.
- Команды `update_stage_local` больше нет: путь, присланный страницей, не копируется в staging. «Из файла» идёт только через `update_pick_installer` (нативный диалог выбирает пользователь).
- Копия старого exe (`--update-watchdog`) ждёт установщик, запускает новую версию без повышения прав и ждёт `health.json {version, ok_at}` 60 секунд; иначе откат прошлым установщиком.
- Прошлый установщик лежит в `<данные>/updates/previous/` вместе со своим `.minisig` и описанием `previous.json {version, sha256, file}` (его читает ядро: `ComponentState.rollback_available`, `previous_version`). Каталог доступен пользователю на запись, поэтому `previous.json` — только подсказка: откат (и `update_rollback`, и watchdog) проверяет прошлый установщик тем же `verify-artifact --allow-older` под тем же дескриптором и требует, чтобы подписанная версия совпала с `previous.json`. Первое обновление после ручной установки отката не имеет: прошлого установщика у приложения нет.
- Остаточные риски отката: (1) ядро для проверки при откате берётся из каталога установки; watchdog — копия СТАРОГО exe, а ядро там уже новое, поэтому его хэш вшитому не равен и не сверяется (каталог Program Files per-machine записываем только администратору); если новая установка повредила ядро, откат не пройдёт проверку (`core_unavailable`). (2) Локальный пользователь, подложивший **настоящий, но более старый подписанный** релиз вместе с его `.minisig` и подправивший `previous.json`, пройдёт проверку подписи при условии совпадения версии; защита от замены старой версии — только сверка версии с `previous.json`, который сам пользовательский. (3) Поиск DLL: рабочий каталог повышенного запуска — System32, но NSIS-установщик ищет библиотеки и рядом с самим exe в каталоге staging/previous, куда пользователь может писать; закрыть это без администратора нельзя (копировать установщик в защищённый каталог могла бы только служба). Подпись и блокировка файла защищают содержимое установщика, но не окружение загрузки его DLL.
- «Установить из файла»: рядом с установщиком может лежать `<имя>.minisig` (его выпускает `updsign artifact`); оболочка копирует его в staging, `VerifyLocalUpdate` проверяет подпись по роли `artifact`, продукт, платформу и что версия новее установленной. Без `.minisig` ядро ищет такой же файл в манифесте онлайн-проверки.

### 12.7 NSIS (Tauri 2): что известно и что не проверено

Выводы из шаблона `tauri-bundler 2.10.4` (`installer.nsi`, `utils.nsh`). Проверки на ВМ (Ф3.0) не было, **допущения подлежат проверке** перед выпуском 0.5.0:

- `/S` — тихая установка. Страницы пропускаются, страница «переустановка» не выполняется: поверх существующей установки файлы заменяются на месте, старый деинсталлятор не вызывается (с `/UPDATE` его вызывают только GUI и пассивный режим).
- `installMode: perMachine` даёт `RequestExecutionLevel admin`: установщик требует повышения сразу при запуске, поэтому запуск идёт через `runas` и показывает один UAC. Каталог — `Program Files\LAVRay` (путь прежней установки берётся из реестра).
- Запущенное приложение: макрос `CheckIfAppIsRunning` через Restart Manager в тихом режиме **принудительно завершает** процессы, держащие `lavray-shell.exe` из каталога установки, без вопросов. Поэтому оболочка заранее останавливает ядро, а наблюдатель — копия exe вне каталога установки (не попадает под Restart Manager).
- Установка более старой версии: `allowDowngrades` в `tauri.conf.json` не задан, по умолчанию в tauri-bundler 2.10.4 это `true` (шаблон отказывает в тихом даунгрейде только при `false`). Откат прошлым установщиком опирается на это допущение.
- Перезапуск: приложение само стартует только с ключом `/R` (без повышения, через `RunAsUser`). Мы `/R` не передаём: запуск делает наблюдатель, чтобы не получить две копии и чтобы проверять heartbeat новой версии.
- Автозапуск при обновлении не снимается (хук `POSTUNINSTALL` проверяет `$UpdateMode`); при тихой установке поверх старой деинсталлятор не запускается вовсе.
- Неизвестно: примет ли UAC и `CreateProcess` установщик, который оболочка держит открытым с запретом записи (`FILE_SHARE_READ`); запустится ли голая копия старого exe без соседних файлов.

### 12.8 Служебные настройки

`update.root_json` (устарел: корни хранятся файлами, §12.3, ключ остаётся служебным и ничем не читается), `update.root_version`, `update.timestamp_version`, `update.serial_stable`, `update.serial_beta`, `update.last_checked_at`, `update.last_url` — служебные (`Internal`): `SetSettings` их не принимает, `GetSettings` не отдаёт, резервная копия исключает (`BackupExclude`). Для пользователя: `update.channel` (`stable`|`beta`) и `update.auto_check` (по умолчанию включено; проверка раз в 6 часов ± 30 минут).

После ротации корня, сменившей ключи роли `timestamp` или `manifest`, соответствующие счётчики (`update.timestamp_version`, `update.serial_*`) сбрасываются: утёкший ключ, однажды подписавший MaxInt64, не может навсегда запереть обновления. Признак смены — версия корня, при которой счётчики были записаны (`update.root_version`), а не факт ротации в этом запуске.

### 12.9 Известные остаточные риски и непроверенное

Не закрыты кодом; записаны, чтобы владелец принимал их осознанно.

1. **Откат принимает любой более старый подписанный релиз.** `update_rollback` и watchdog проверяют подпись и совпадение версии с `previous.json`, но сам `previous.json` лежит в каталоге пользователя без аутентификации. Локальный пользователь, подложивший настоящий старый релиз с его `.minisig` и правку `previous.json`, пройдёт проверку. Версионной планки отката («не старше N») нет.
2. **Watchdog не привязан к хэшу ядра в portable-раскладке.** Watchdog — копия старого exe, а встроенное ядро в каталоге установки к этому моменту уже новое, поэтому вшитый хэш не сверяется (`bundled_core(.., None)`). В per-machine установке каталог доступен на запись только администратору; в распакованной portable-папке пользователя подмена `lavray-core.exe` обесценила бы `verify-artifact` при откате.
3. **Поиск DLL начинается в каталоге staging/previous.** Рабочий каталог повышенного запуска — `System32`, но установщик NSIS ищет библиотеки и рядом с собственным exe, а в этот каталог пользователь может писать. Подпись и блокировка защищают содержимое установщика, но не окружение загрузки его DLL; закрыть это без службы с правами администратора нельзя.
4. **Не проверено: принимают ли UAC и `CreateProcess` установщик, который оболочка держит открытым с запретом записи (`FILE_SHARE_READ`).** Проверить на тестовой ВМ до выпуска 0.5.0. Если нет, `ShellExecuteExW` вернёт `ERROR_SHARING_VIOLATION` (32): код ответит ясно — `installer_locked` (для отката тот же код в `last-update.json`), без повторов; ядро возвращается перезапуском оболочки, замок снят, пользователь повторяет сам. Тогда дескриптор придётся отпускать перед `runas` (потеряв защиту от подмены в этот промежуток, но не защиту подписью: подпись проверена под дескриптором, а NSIS проверяет собственную целостность).

### 12.10 Пресеты и гео-данные через апдейтер (T-75, часть 7.5)

Секции `presets` и `geo` подписанного манифеста (§3.3) доставляются без установщика и без перезапуска приложения. Файлы не подписываются по отдельности: их целостность держит sha256 в манифесте, который подписан ключом `manifest` (r1).

**Формат гео-набора.** `geo.path` указывает на zip (не tar.zst, как в раннем наброске §3.3: zstd нет в стандартной библиотеке, а новых модулей проект не берёт). Допустимы только записи `geoip/<имя>.srs` и `geosite/<имя>.srs`: это раскладка каталога поставки `<GeoDir>/<kind>/<name>.srs` (`cfgbuild/route.go`). Имя из `[A-Za-z0-9@!._-]`, без `..`, без зарезервированных имён Windows, без повторов с точностью до регистра. Отвергаются: каталоги, абсолютные пути, обратные слэши, диски и `:`, ссылки и прочие не обычные файлы, шифрованные записи, чужие методы сжатия. Лимиты: 64 МиБ сам архив; не больше 512 записей, 32 МиБ на файл, 256 МиБ всего, сжатие не больше 100 раз у файлов крупнее 64 КиБ; размеры проверяются по заголовкам до чтения и по факту при чтении. Каждый файл обязан быть корректным `.srs`, а набор — содержать все файлы встроенного (иначе пресет, ссылающийся на отсутствующий набор, не запустится).

**Применение гео.** Архив распаковывается во временный каталог рядом с `<данные>/geo`, туда же пишутся `revision.txt` (ревизия выше встроенной: `EnsureGeo` оставляет такой набор) и `source.json` (sha256 и дата среза). Затем `geo.prev` откладывается, `geo` переименовывается в `geo.prev`, новый каталог встаёт на место `geo`; любой сбой возвращает всё как было. Откат (`Rollback(GEO)`) возвращает `geo.prev`; прошлая ревизия одна. `GeoDir` конфигурации всегда указывает на `<данные>/geo`, то есть на действующий набор. Тот же архив повторно не применяется (признак — sha256 в `source.json`).

**Применение пресетов.** Принимается набор, у которого: id встроенный; sha256 файла равен манифесту; `revision` файла равна `rev` манифеста и выше действующей; `builtin=true`; набор проходит `presets.Validate`. Пачка проверяется целиком до записи. Запись — каталогом `<данные>/presets/override` целиком (те же временный каталог, `override.prev` и откат). `BuiltinPresetsWith(dir)` берёт файл `<id>.json` только для id встроенных наборов и только при более высокой ревизии, чем встроенная: чужой id, `builtin=false`, битый или огромный файл молча пропускаются, действует встроенный набор. Пользовательские копии лежат в базе и не затрагиваются; у копий, снятых с обновлённого набора, `source_updated` становится true, «Сбросить к исходному» берёт новые правила.

**RPC.** `CheckUpdates` предлагает `PRESETS` (строки `lav-ru:3, lav-cn:5`) и `GEO` (дата среза). `DownloadUpdates` с `components=[PRESETS|GEO]` кладёт проверенные файлы в `<данные>/updates/staging/components` и шлёт `verified`; пустой список по-прежнему означает только приложение. `ApplyUpdates` без скачанного артефакта — FAILED_PRECONDITION `not_staged`; файл перечитывается и сверяется заново; параллельное применение или откат — ABORTED; нарушение целостности или безопасности — событие `verify_failed` с причиной (`sha256_mismatch`, `truncated`, `too_large`, `not_newer`, `preset_rejected`, `archive_unsafe`, `archive_limits`, `geo_incomplete`, `geo_invalid`) и очистка staging; успех — событие `applied` (`presets` | `geo`). `Rollback(PRESETS|GEO)` без прошлой ревизии — FAILED_PRECONDITION `no_previous`; занятый каталог — FAILED_PRECONDITION `dir_busy`. Решения для агентов не менялись: deny у CheckUpdates, DownloadUpdates, ApplyUpdates и Rollback, read у GetUpdateState.

**Перезапуск профиля.** При работающей сессии `ApplyUpdates` шлёт `ready_for_restart` с причиной `profile`, если изменился активный набор или гео-набор, а `RollbackResponse.needs_profile_restart` сообщает то же об откате. Работающий sing-box уже прочитал правила, новые данные он увидит после переподключения.

**Не сделано и не проверено.** (1) `updsign` пока не собирает секции `presets` и `geo` манифеста и zip-архив гео: клиентская сторона готова, выпускающая — нет. (2) Подмена каталога `<данные>/geo` при работающем соединении на Windows не проверялась вживую: если sing-box держит файлы набора открытыми, переименование каталога может вернуть отказ; тогда применение завершится ошибкой `dir_busy` и прежний набор останется на месте (см. отключение VPN и повтор).
