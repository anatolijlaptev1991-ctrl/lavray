# Спайк R0-C: Connect JSON на Rust

Вопрос R-3 плана переноса: может ли Rust отдавать UI тот же протокол, что сейчас отдаёт Go-ядро, и во что это обходится по задержкам. Код: `spikes/connect-json-rs/` (отдельный `[workspace]`, ни `shell/`, ни будущий `rust/` не затронуты).

**Итог в трёх строках.** Свой слой на `hyper` (≈700 строк, включая модульные тесты) обслужил настоящий клиент UI (`connect-web`, JSON) без единого расхождения с Go в проверенных вызовах. На loopback протокольный слой Rust лишь немного быстрее Go (≈40 мкс на запрос при равной работе); большая разница на `GetStatus` целиком из SQLite, а не из языка. Решение по `connectrpc` спайком не принимается (крейта нет в локальном кэше), но главный риск R-3 сместился: это не конверты Connect, а канонический proto3-JSON для 95 RPC.

## 1. Что сделано

| Часть | Файлы |
|---|---|
| Сервер: unary `CoreService/GetStatus` и `ProfileService/StopTests`, server-streaming `CoreService/SubscribeEvents` | `src/{handler,request,stream,envelope,error,auth,cors,status,server}.rs` |
| Тесты (unary, стрим, 401, ошибки): `cargo test --offline --locked`, 8 тестов | `src/*` (модульные), `tests/{unary,stream}.rs` |
| Клиент совместимости: настоящий `connect-web` + `ui/src/gen` + `coreAuth.ts` | `js/compat.ts`, `js/run-compat.mjs`, `js/raw-checks.mjs` |
| Замер | `js/bench.mjs`, `js/bench-lib.mjs`, `js/servers.mjs`, `src/bin/loadgen.rs` |

Зависимости только из кэша: `hyper 1.12`, `hyper-util`, `http-body-util`, `tokio`, `bytes`, `futures-util`, `serde_json`. Ответы строятся `serde_json::json!` вручную, без `prost`: форма повторяет protojson Go (нулевой enum опущен, `int64` строкой, lowerCamelCase). Сервер читает токен со stdin и печатает `LAVRAY_CORE_READY tcp://…`, как Go-ядро.

Повторить: `cargo build --release` в `spikes/connect-json-rs/`; Go-ядро собрать как в `scripts/smoke/smoke_core.py`; `node js/run-compat.mjs --go … --rust … --work DIR` и `node js/bench.mjs --go … --rust … --loadgen … --work DIR`. Для TS-клиента нужен `ui/node_modules` (`NODE_MODULES=…`): `esbuild` из него собирает `compat.ts` в один `.mjs`, `tsx` не нужен.

## 2. Методика замера

- Loopback `127.0.0.1`, порты выдаёт ОС (не 2080); Go-ядро: `lavray-core serve --listen-socket 127.0.0.1:0 --data <tmp>`, токен по stdin, сборка с `BUILD_TAGS`, `CGO_ENABLED=0`. Rust: `--release` (`lto=thin`, `panic=abort`).
- Оба сервера живут одновременно; в каждом из 10 прогонов порядок Rust/Go чередуется (дрейф фона делится поровну).
- Прогон = на каждый RPC: прогрев 1000, затем 10 000 последовательных вызовов по одному соединению и 50 параллельных потоков по 200 вызовов (keep-alive, по соединению на поток); плюс 500 открытий `SubscribeEvents` до первого целого кадра.
- Два клиента: **нативный** (`loadgen`, hyper, 4 потока tokio; малые накладные) и **Node** (`node:http`, один поток; ближе к UI, но на 50 потоках сам упирается в ≈7 тыс. rps).
- В таблице: медиана p50/p99 по 10 прогонам и (в скобках) CV p50/p99 между прогонами. RSS: `WorkingSet64`/`PeakWorkingSet64`/`PrivateMemorySize64` сервера через PowerShell.
- **Сравнение честное только для `StopTests`**: это самый дешёвый RPC Go без БД (`s.cancelTestBatches()` → `{}`). `GetStatus` в Go делает 6 чтений SQLite (`settingJSON` → `st.GetSetting`: `inbound.address/port`, `inbound.auth.user/pass`, `tun.interface_name`, пресет); у Rust-спайка статус константный.

| StopTests, 50 параллельных, нативный | 683 (11%) | 640 (5%) | 1564 (22%) | 5104 (59%) |
| StopTests, 10 000 последоват., Node | 188 (5%) | 224 (6%) | 649 (35%) | 1203 (60%) |
| StopTests, 50 параллельных, Node | 6958 (5%) | 7411 (5%) | 10135 (9%) | 10808 (50%) |
| GetStatus, 10 000 последоват., нативный | 111 (12%) | 353 (7%) | 333 (79%) | 1540 (60%) |
| GetStatus, 50 параллельных, нативный | 702 (6%) | 13484 (11%) | 1597 (20%) | 33647 (15%) |
| GetStatus, 10 000 последоват., Node | 194 (5%) | 431 (6%) | 482 (62%) | 1484 (58%) |
| GetStatus, 50 параллельных, Node | 7186 (11%) | 12696 (8%) | 9746 (47%) | 31949 (11%) |
| SubscribeEvents, до первого кадра | 715 (8%) | 970 (13%) | 1541 (30%) | 2340 (96%) |

Пропускная способность на 50 потоках, нативный клиент (медиана, rps): `StopTests` 67 077 / 54 644; `GetStatus` 64 072 / 3 600 (Rust / Go). На Node-клиенте оба сервера упираются в клиента (≈7 тыс. rps у `StopTests`).

Память сервера (МиБ, рабочий набор): Rust 5.7 до нагрузки, 9.2 после, пик 9.8, private 6.7; Go 25.8, 40.8, пик 50.4, private 67.1. Это сравнение «пустой спайк против полного ядра» (sing-box, SQLite, сервисы), поэтому как оценка выигрыша по памяти не годится.

Как читать:
- p50 при равной работе (`StopTests`): Rust быстрее на ≈35–45 мкс последовательно, на 50 потоках — паритет (клиент и планировщик ОС, а не сервер, определяют цифру). Разница протокольных слоёв на loopback мала.
- Хвосты (p99) у Rust ниже в 2–3 раза на нативном клиенте, но CV p99 между прогонами 20–95 %: это шум ПК, а не устойчивая цифра. Устойчиво только p50 (CV 5–13 %).
- `GetStatus`: ×3 (последовательно) и ×19 (50 потоков) — это стоимость 6 SQL-чтений под нагрузкой, она совпадает с наблюдением аудита и исправима в Go (кэш настроек), см. п. 6 плана. Относить её на счёт Rust нельзя.
- Rust-хендлер не сериализует настоящий protobuf; реальная работа с `prost`+JSON добавит время и к серверу, и к 95 RPC.

## 4. Совместимость с `connect-web`

Клиент — `createConnectTransport({useBinaryFormat:false})` v2.2 + `authInterceptors` из `ui/src/lib/coreAuth.ts` + `CoreService`/`ProfileService` из `ui/src/gen/lavray_pb.ts`. Один и тот же набор вызовов к Go и Rust, результаты сравнены после замены `tsMs`:

| Проверка | Итог |
|---|---|
| unary `getStatus`, `stopTests` (Bearer) | совпало с Go, включая декодирование enum и `int64` в `bigint` |
| `subscribeEvents`: первый кадр-снимок, отмена `AbortController` | совпало |
| без токена и с чужим токеном (unary и стрим) | оба: `ConnectError` с кодом `Unauthenticated` |
| Rust-только: серия кадров + пустой end-stream | клиент получил 4 события и чистое завершение |
| Rust-только: ошибка в end-stream (`{"error":{...}}`) | `ConnectError` `Internal`, `rawMessage` доехал |

Сырой HTTP (`js/raw-checks.mjs`, Go и Rust, сравнены статус, `content-type`, код, CORS-заголовки): плохой JSON (400 `invalid_argument`), неверный `Content-Type` (415), `GET` на RPC, неизвестный путь (404), 401 без токена и с «голым» токеном, `/healthz`, preflight `OPTIONS`, CORS на POST для `tauri.localhost`, чужой origin без CORS-заголовков: **все совпали**.

Единственное расхождение: тело сообщения > 16 МиБ. Go отвечает `429 resource_exhausted`; Rust отвечает тем же и закрывает соединение, не дочитав тело, поэтому Node-клиент видит `ECONNRESET` раньше ответа. Для продакшена нужно дочитывать (с потолком) или закрывать мягко.

**Не проверено:** режим cookie+CSRF, бинарный `application/proto`, `useHttpGet`, gzip, `timeoutMs` клиента (сервер `Connect-Timeout-Ms` понимает, тест на клиенте не делался), реальный webview Tauri, HTTP/2, gRPC/gRPC-web, остальные 93 RPC, длительные и многочисленные стримы, UDS и named pipe.

## 5. Выводы по R-3

1. **Протокол Connect на hyper прост и укладывается в малый код.** Unary + стрим в JSON — это маршрутизация по пути, проверка `Content-Type`, 5-байтные конверты, end-stream и таблица кодов. Модули `envelope`, `error`, `auth`, `cors`, `request` ≈ 320 строк и с `connectrpc` не пересекаются по сложности.
2. **Сложность R-3 не в Connect, а в proto3-JSON.** Спайк строил JSON вручную для двух сообщений. Для 2 411 строк proto (16 сервисов, 95 RPC, `oneof`, `optional`, enum по имени, `int64` строкой, `bytes`, вложенные карты) нужен генератор. В кэше нет ни `pbjson(-build)`, ни `prost-reflect`, ни `prost-build`, поэтому ни один вариант с кодогенерацией офлайн не проверен.
3. **`connectrpc` (connect-rust) 0.7, pre-1.0.** Не вошёл в кэш, оценить его по факту нельзя. По `PLAN.md` и `research-2026-11-08.md` (самоописание проекта, не проверено): он берёт на себя маршрутизацию, конверты, сжатие, ошибки и кодогенерацию сервисов. Выигрыш — сгенерированные трейты для 16 сервисов и готовый JSON-кодек вместо нашего слоя, цена — зависимость от pre-1.0 API и своего protobuf-стека (`buffa`). Что нужно проверить при доступе к сети: JSON-кодек для `oneof`/`optional`/`int64`, server-streaming с `Connect-Timeout-Ms` и отменой, порядок заголовков 401/CORS (они вне RPC), размер бинаря и время сборки.
4. **Рекомендация.** Держать путь «свой тонкий слой на hyper» как рабочий запасной вариант: он доказан для unary и стримов. Решение «`connectrpc` или свой слой» принимать после короткого второго спайка с сетью: тот же клиент `run-compat.mjs`, ещё 3–4 RPC разной формы (`oneof`, `optional int64`, `repeated`, `map`), JSON через `pbjson` против `connectrpc`. Тест уже готов, меняется только сервер.
5. **Выигрыш по задержкам на loopback от самой смены языка мал** (≈35–45 мкс на запрос; на 50 потоках — паритет). Оправдание переноса control plane из этих цифр не вытекает; сильнее всего влияет не язык, а обращения к БД (`GetStatus`).

## 6. Что нужно для продакшена (не сделано в спайке)

| Область | Состояние в спайке | Что нужно |
|---|---|---|
| Лимит тела | 16 МиБ через `Limited` и `Content-Length`; для превышения — `ECONNRESET` | дочитывать/дренировать с потолком, ответ до закрытия; лимит на конверт стрима отдельно |
| Таймауты | `Connect-Timeout-Ms` для unary, `header_read_timeout` 10 с | таймаут стрима и простоя соединения (`hyper` не даёт `IdleTimeout`, нужен свой), отмена хендлера при уходе клиента (для стрима есть) |
| Сжатие | нет; `Content-Encoding`/`Connect-Content-Encoding` ≠ identity → `unimplemented` | gzip (`flate2`, `async-compression` есть в кэше) для запроса и ответа, `Accept-Encoding`, флаг сжатия в конверте |
| Ошибки | 6 кодов из 16, детали (`ErrorInfo`, `errorReason`) не передаются | полная таблица кодов, поле `details`, `errorReason` как в Go, перехватчик с `recover` |
| CORS/Origin | перенос `cors.go`: список origin и loopback | проверка `Origin` на CSRF-путях веб-режима, cookie-режим и `X-LAVRay-CSRF`, WebSession |
| Авторизация | Bearer как в Go, сравнение за постоянное время, 401 побайтно | агентский токен, cookie-сессии, `/healthz` |
| Транспорт | HTTP/1.1 на TCP | UDS и named pipe, HTTP/2 при необходимости, лимит числа соединений и стримов |
| Остальное | 2 unary + 1 стрим | кодогенерация 95 RPC, `buf breaking`, дифференциальный харнесс Go↔Rust на общих входах |

## 7. Ограничения замера

- Один хост (Ryzen 7 5800X3D, Windows 11), только loopback; ни сети, ни TLS, ни реальных профилей.
- Рабочий ПК владельца: в фоне живой VPN и десктопные процессы. Шум виден в CV p99 (до 95 %); поэтому надёжны только медианы p50, p99 — ориентир.
- Клиент (Node и даже `loadgen`) делит CPU и планировщик с серверами; на 50 потоках p50 ≈ очередь клиента, а не задержка сервера.
- Rust-сервер без бизнес-логики и без настоящего protobuf; Go-ядро полное (интерсепторы, журналирование, БД). `StopTests` — единственная пара с близкой работой, и она отражает именно протокольный слой.
- Память: полное ядро против пустого спайка; пик Go включает рост кучи при нагрузке.
- Go-ядро собрано из `95802f4`, без изменения `core/`; холодный старт и подключение к серверам не измерялись, `Connect` ядра не вызывался.
