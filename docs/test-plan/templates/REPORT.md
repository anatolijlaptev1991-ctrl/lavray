# Шаблон отчёта по одному файлу плана

Скопируйте блок ниже в `results/<ID>.md` (например, `results/A07.md`) и заполните. Все поля обязательны; если поле неприменимо, пишите `н/п` и причину. Отчёт пишет исполнитель файла (субагент или человек); оркестратор его не переписывает, а только проверяет (раздел 6 файла `00-README.md`) и копирует итог в `results/SUMMARY.md`.

Статусы, которыми можно пользоваться (других нет):

| Статус | Когда ставить |
|---|---|
| `PASS` | Все обязательные шаги выполнены, все критерии PASS файла выполнены |
| `FAIL` | Хотя бы один критерий PASS не выполнен, а предусловия соблюдены. Причина всегда в разделе «Дефекты» |
| `BLOCKED` | Шаг нельзя выполнить из-за внешнего: нет сети, нет релиза, нет прав, нет доступа к репозиторию. Это не дефект продукта; в отчёте указано, что именно блокирует и кто может снять |
| `SKIPPED` | Шаг или файл пропущен по явному условию самого файла (например, не задан флаг `LAVRAY_ALLOW_TUN=1`) |
| `PARTIAL` | Только для файла целиком: часть шагов `PASS`, часть `BLOCKED` или `SKIPPED`, и нет ни одного `FAIL` |

Для отдельного шага допустим ещё статус `WARN`: проверка помечена в файле как «наблюдение» (например, `WARN log.singbox_inbound_lines_expected_at_info` в A07). Он не меняет итог файла, но обязан попасть в раздел «Дефекты» с серьёзностью, указанной в файле.

Правило итога файла: есть хотя бы один `FAIL` — итог `FAIL`; иначе есть `BLOCKED` или `SKIPPED` у обязательных шагов — `PARTIAL`; иначе `PASS`. Файл, который нельзя было начать (не прошёл страж «тестовый ПК»), получает итог `BLOCKED` и ни одного выполненного шага.

Серьёзность дефекта: `critical` (утечка секрета, выполнение чужого кода, потеря данных, необратимое изменение системы), `major` (функция не работает, защита обходится, откат не вернул систему), `minor` (локальный дефект, обходной путь есть), `doc` (ошибка самого плана или документации, продукт верен).
