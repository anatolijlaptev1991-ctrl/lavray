# План тестирования LAVRay: инструкция для оркестратора ZCode

Это точка входа. Документ читает агент ZCode (Claude Code) на **тестовом ПК**, а владелец проекта даёт ему короткий промпт из раздела 9. Агент-оркестратор готовит окружение, запускает по одному субагенту на каждый файл плана, собирает отчёты `results/<ID>.md` и пишет сводку `results/SUMMARY.md`. Ручные файлы (`manual/`) выполняет человек или агент с управлением экраном.

## 1. Что покрывает план

План проверяет итоговый релиз **v0.9.0**. Во всех файлах плана `<TAG>` означает `v0.9.0` (в `env.ps1`: `LAVRAY_REF = v0.9.0`, `LAVRAY_VERSION = 0.9.0`, прежняя версия для проверки обновления поверх — `0.3.0`). Релиз состоит из **семи** файлов: `LAVRay-0.9.0-x64-setup.exe`, `LAVRay-0.9.0-portable-x64.zip`, `SHA256SUMS.txt`, `lavray-core-linux-amd64`, `lavray-core-linux-arm64` (оба с тегом `with_webui`), `ui-dist.tar.gz`, `SHA256SUMS-linux.txt`; каталога `meta/` (подписанные метаданные обновлений) в нём нет, потому что ключей подписи пока не создано и задание `sign` пропускает себя (это не дефект, A06 шаг 17).

**Часть 1** — основа, существовавшая к версии **0.4.0** (выпуски 0.1.0–0.4.0, фазы Ф1 и Ф2 плана доработки):

- ядро на Go с sing-box, API ConnectRPC, хранилище SQLite, импорт ссылок и подписок, сборщик конфигов, туннель, REALITY/uTLS, проверка связи после подключения;
- MCP для ИИ-агентов (`lavray-core mcp`, режимы «только чтение» и «чтение и управление»);
- Ф1: подтверждение custom-полей по хэшу (T-08B), экран «Соединения», скорость и учёт трафика (T-79), инфраструктура проверок (Ф1.0);
- Ф2: окно, трей, уведомления, глобальное сочетание, «Сохранить как», прокси для VPN-подключений Windows (T-82), показ и импорт QR-кодов (T-77);
- установщик NSIS, портативный ZIP, контрольные суммы.

**Часть 2** добавляет области, вошедшие в `v0.9.0` (написана по коду `main` на `773b4e8`, тег может быть ещё не выпущен):

- редактор наборов маршрутов T-80 (пять встроенных наборов, свои наборы, ревизии, импорт и экспорт, маршрут NekoRay) и зашифрованная резервная копия T-83 (`LAVBK1`, Argon2id + XChaCha20-Poly1305);
- хвосты A ядра: очистка недоступных серверов и дубликатов, разрешение доменов, выгрузка конфига, сброс настроек, подписка на настройки, запоминание профиля, читатели настроек, CORS;
- веб-панель T-76 (`--web-bind`: первый администратор, вход, CSRF, блокировка, сессии, TLS, заголовки) и её Playwright-спецификация;
- перенос из NekoBox T-78 (`MigrationService`: поиск установок, предпросмотр, перенос, повтор без дублей, подкоманда `lavray-core import-nekobox`);
- хвосты B (в `main` с `773b4e8`): kill switch системного прокси (`connect.kill_switch_proxy`), транспорт XHTTP как «сохранён, но не собирается» (`transport_unsupported`, `Profile.unsupported_reason`), правая панель «Подключение» (внешний IP через туннель, удалённый DNS, без строки «Потери»), меню строки сервера, диалог очистки, «Обновить все», откат подписки, сводка трафика группы, конфиг ядра в диагностике, защита `rpc_usage`;
- центр обновлений T-75 (цепочка доверия «корень → timestamp → manifest», загрузка и проверка подписи, `verify-artifact`, установка, откат и сторож оболочки; **пресеты и гео-данные через апдейтер** (T-75 §7.5): `updsign geo-pack`, секции `presets` и `geo` манифеста, применение и откат без перезапуска приложения, защита от враждебных архивов). Корень доверия в релизах пока **заглушка** (владелец ещё не провёл церемонию ключей, в релизе нет `meta/`), поэтому все проверки идут на **тестовом корне**, который тестировщик создаёт сам (A13, M12); настоящий выпуск проверяется после церемонии ключей;
- обновление с 0.3.0 на 0.9.0 на реальных данных: база SQLite схемы 4 доводится до схемы 6 без потерь (A10 шаги 4, 6, 9; M01 пп. 2.13, 3.9–3.12).

Файлы рассчитаны на тег `<TAG>` = `v0.9.0` (в `env.ps1` это `LAVRAY_REF`). Пока тег не опубликован, их выполняют на `main` не старее `773b4e8`; в отчёте указывайте фактический коммит ядра. Пресеты и geo через обновления (T-75 §7.5, PR #19, `dce8ba0`) проверяют A13 (раздел «§7.5 наборы и geo») и M12 (часть 13).

Связанные документы репозитория: `docs/TEST-PLAN.md` (общие наборы тестов и бюджеты), `docs/RELEASE-CHECKLIST.md` (чек-лист публичного выпуска), `docs/MCP.md`, `docs/RELEASE-NOTES-windows-v0.3.0.md`, `docs/RELEASE-NOTES-windows-v0.4.0.md` (заметки к 0.9.0 берите из описания релиза: `gh release view v0.9.0 -R anatolijlaptev1991-ctrl/lavray`).

## 4. Правила безопасности (для оркестратора и всех субагентов)

1. **Только тестовый ПК.** Опасные файлы (прокси, TUN, реестр, установка, данные приложения; автоматические и ручные) выполняются только после стража из `01-ENVIRONMENT.md`, раздел 3, и только пока `Test-TestPc` (функция из `env.ps1`) возвращает `True`: маркер `C:\lavray-test\TESTPC_OK` есть, создан на этом ПК и не старше 30 суток. Это относится и к ручным файлам. Страж отказывается, если видит работающий VPN, запущенные `nekobox`, `nekoray`, `LAVRay`, адаптеры `neko-tun`/`wintun`/`wireguard`, занятый порт 2080, включённый системный прокси или PAC. Подтверждение «это тестовый ПК» даёт только владелец переменной `LAVRAY_TESTPC_CONFIRMED=YES-DISPOSABLE`; оркестратор задавать её не вправе.
2. **Опасные файлы идут по одному.** Никакие два файла с опасностью, отличной от «нет», не работают одновременно; S-файлы не запускаются одновременно ни с A07 и A08 (те держат процессы `lavray-core` и порты), ни с M-файлами.
3. **Продукт не правится.** Ни исходники, ни настройки репозитория; всё, что меняет файлы репозитория, делается в рабочей копии `wt\<ID>`.
4. **Секретов нет в отчётах.** Ссылка тестовой подписки (`LAVRAY_TEST_SUB_URL`), токены, содержимое `agent-endpoint.json`, пароли заменяются на `***`. Переменные окружения с секретами не печатаются.
5. **Откат обязателен.** Раздел «Откат» файла выполняется всегда, даже при провале. Файл, после отката которого система не равна исходной (прокси, адаптер, запись VPN, установка), получает `FAIL` с серьёзностью `critical` и останавливает дальнейшие опасные файлы до решения владельца.
6. **Не публиковать и не отправлять.** Результаты остаются в `C:\lavray-test\results`. Ничего не отправляется во внешние сервисы, кроме скачивания ассетов и пакетов, оговорённого планом.
7. **Не отключать защиту ПК.** Антивирус, SmartScreen, брандмауэр и UAC не отключаются. Файл, который из-за них нельзя выполнить, получает `BLOCKED`.

## 5. Параллельность и порядок

### 5.1 Группы

- **P (parallel)** — файлы без опасности. Работают параллельно (каждый в своём `wt\<ID>` и `tmp\<ID>`), но не более трёх тяжёлых одновременно (A02, A03, A05, A12, A13 нагружают процессор и диск). Файлы A09, A12, A13, A14 и A15 держат свои процессы `lavray-core` на случайных loopback-портах и в собственных каталогах `tmp\<ID>`, поэтому с A07 и A08 не пересекаются. A15 на несколько секунд запускает копию `PING.EXE` под именем `nekobox.exe` (проверка признака «NekoBox запущен»); не проверяйте в это время страж из `01-ENVIRONMENT.md` и не запускайте A15 параллельно с файлами группы S.
- **S (serial)** — файлы, меняющие прокси, реестр или установку: A04, A11, A10. Выполняются строго по одному, **после** окончания всех P-файлов и в порядке A04, затем A11, затем A10.
- **M (manual)** — ручные файлы. Идут по одному, после S, в порядке M01, M02, M03, M04, M05, M06, M07, M08, M09, M10, M11, M13, M14, M15, M16, M17, M18, M12 (последним: он ставит другие версии программы и работает на ВМ со снимком, после него ПК возвращают к снимку): они работают с одной установленной копией программы и одним окном. M10 (часть 5) и M11 (часть 6) подменяют или заменяют базу данных приложения (с копией каталога данных заранее), поэтому стоят после M09 и перед M17, а M16 не требует установленной программы и использует ядро из A12.

## 6. Как запускать субагентов и собирать результаты

### 6.1 Один субагент на файл

Оркестратор создаёт для каждого файла отдельного субагента (инструмент `Agent`, тип по умолчанию, модель Sonnet; для A01, A05, A06, A08 достаточно Haiku) и передаёт ему промпт ниже. Субагент читает **только** свой файл и `01-ENVIRONMENT.md` (разделы 2–4 и 8–10), поэтому каждый файл самодостаточен. Подставьте `<ID>` и `<путь к файлу>` (например, `auto\A07-core-smoke.md`):

```text
Ты исполнитель одного файла плана тестирования LAVRay. Прочитай только два файла:
C:\lavray-test\plan\docs\test-plan\<путь к файлу> и C:\lavray-test\plan\docs\test-plan\01-ENVIRONMENT.md.
Первой командой выполни: . C:\lavray-test\env.ps1
Правила:
1. Выполняй шаги файла по порядку, ничего не придумывай. Если команда в файле не работает так, как написано,
   запиши в отчёт дефект с серьёзностью doc и фактическую рабочую команду, затем иди дальше.
2. Если у файла опасность не «нет» (это же правило для ручных файлов manual\: человек или агент с экраном проверяют
   до первого действия), сначала выполни Test-TestPc из env.ps1: маркер C:\lavray-test\TESTPC_OK есть, создан на этом ПК,
   не старше 30 суток. Не True: итог BLOCKED, ни одного шага.
3. Не правь продукт, не запускай шаги других файлов, не отключай защиту ПК, не печатай секреты (токены, LAVRAY_TEST_SUB_URL).
4. Раздел «Откат / уборка» выполни обязательно, даже если шаги провалились; проверь, что система вернулась.
5. Результат: создай C:\lavray-test\results\<ID>.md строго по шаблону из
   C:\lavray-test\plan\docs\test-plan\templates\REPORT.md (скопируй из него блок markdown),
   вложения клади в C:\lavray-test\results\<ID>\.
6. Последним сообщением ответь ровно одной строкой: <ID> <ИТОГ> <шагов PASS>/<всего> C:\lavray-test\results\<ID>.md
Файл, который выполняешь: <ID>.
```

Для ручных файлов (`manual/`) вместо субагента отчёт заполняет человек или агент с управлением экраном по тому же шаблону; правило 2 (проверка маркера командой `Test-TestPc` до первого действия) действует и для них.

### 6.2 Проверка отчёта

Оркестратор проверяет каждый присланный отчёт: файл существует, в нём есть строка `| Итог | <статус> |` с допустимым статусом и разделы 1, 2, 4, 6. Функции сохраните как `C:\lavray-test\report-tools.ps1`:

```powershell
function Test-Report {
  param([string]$Id, [string]$Dir = 'C:\lavray-test\results')
  $p = Join-Path $Dir "$Id.md"
  if (-not (Test-Path $p)) { return [pscustomobject]@{ Id = $Id; Ok = $false; Status = ''; Problem = 'нет файла отчёта' } }
  $t = Get-Content $p -Raw
  $m = [regex]::Match($t, '\|\s*Итог\s*\|\s*(PASS|FAIL|BLOCKED|PARTIAL|SKIPPED)\s*\|')
  $missing = @('## 1. Шаги', '## 2. Критерии', '## 4. Дефекты', '## 6. Откат') | Where-Object { -not $t.Contains($_) }
  $problem = @()
  if (-not $m.Success) { $problem += 'нет строки «Итог» с допустимым статусом' }
  if ($missing) { $problem += ('нет разделов: ' + ($missing -join ', ')) }
  [pscustomobject]@{ Id = $Id; Ok = ($problem.Count -eq 0); Status = $m.Groups[1].Value; Problem = ($problem -join '; ') }
}

# Числа для таблицы сводки: шагов PASS / всего и дефекты critical/major/minor/doc.
function Get-ReportRow {
  param([string]$Id, [string]$Dir = 'C:\lavray-test\results')
  $t = Get-Content (Join-Path $Dir "$Id.md") -Raw
  $steps = [regex]::Matches($t, '(?m)^\|\s*\d+(\.\d+)?\s*\|\s*(PASS|FAIL|BLOCKED|SKIPPED|WARN)\s*\|')
  $pass = @($steps | Where-Object { $_.Groups[2].Value -eq 'PASS' }).Count
  $sev = [regex]::Matches($t, '(?m)^- Серьёзность:\s*(critical|major|minor|doc)')
  $c = @{ critical = 0; major = 0; minor = 0; doc = 0 }
  foreach ($s in $sev) { $c[$s.Groups[1].Value]++ }
  [pscustomobject]@{ Id = $Id; Steps = "$pass / $($steps.Count)"; Defects = "$($c.critical)/$($c.major)/$($c.minor)/$($c.doc)" }
}
```

Использование:

```powershell
. C:\lavray-test\report-tools.ps1
$ids = 'A01', 'A02', 'A03', 'A04', 'A05', 'A06', 'A07', 'A08', 'A09', 'A10', 'A11', 'A12', 'A13', 'A14', 'A15'
$ids | ForEach-Object { Test-Report -Id $_ } | Format-Table Id, Ok, Status, Problem -AutoSize
```

Отчёт с `Ok = False` возвращается исполнителю один раз с текстом `Problem`; второй сбой оркестратор записывает в сводку как «отчёт неполный» и берёт статус из последней строки ответа субагента.

### 6.3 Каталог результатов

```text
C:\lavray-test\results\
  A01.md … A11.md, M01.md …      отчёты по шаблону templates\REPORT.md
  A01\ … A11\ …                  вложения (вывод команд, журналы, скриншоты)
  SUMMARY.md                     сводка по шаблону templates\SUMMARY.md
```

### 6.4 Сводка

После всех отчётов оркестратор:

1. строит таблицу «Итоги по файлам» цифрами из `Get-ReportRow` и статусами из `Test-Report`;
2. переносит дефекты по тяжести (critical, major, minor), отдельно `doc` — это правки плана;
3. выписывает `BLOCKED` и `SKIPPED` с причинами и тем, кто их снимает;
4. сверяет покрытие с `coverage-matrix.md`: какие строки остались без выполненного покрытия;
5. фиксирует состояние ПК после прогона по шаблону (раздел «Состояние тестового ПК после прогона»);
6. ставит рекомендацию по правилу из `templates/SUMMARY.md` (`GO`, `GO с оговорками`, `NO-GO`). Решение «выпускать или нет» принимает владелец.

Обязательные для рекомендации `GO` файлы: A01–A08, A10, A11, M01, M03, M06, M17; а также A09, A12, A13, A14, A15, M10, M11 и M16, если соответствующий код (T-80, T-83, хвосты A, T-76, T-78, T-75) входит в проверяемый выпуск. M12 обязателен для `GO` после церемонии ключей владельца (настоящий корень) и всегда содержит запись опыта с запретом записи на ВМ (часть 10). Для v0.9.0 без `meta/` обновление проверяется только на тестовом корне (A13, M12), это не причина для `NO-GO`. Для A10 и M01 обязательны миграция базы 4 → 6 (К10 в A10, К9 в M01) и сохранение данных. Остальные ручные файлы могут быть `PARTIAL`.

### 6.5 Как сообщать о сбоях

- `FAIL` — это результат, а не повод чинить продукт: оркестратор ничего не правит и не перезапускает файл «до зелёного». Допускается один повтор файла, если сбой вызван сетью (таймаут скачивания, разрыв при `npm ci`/`cargo`); повтор записывается в «Отклонения».
- Каждый дефект описан в отчёте файла по шаблону (серьёзность, шаг, ожидали, получили, воспроизведение, доказательство).
- Дефект самого плана (неверная команда, неверная метка интерфейса, устаревшее число) помечается `doc` вместе с рабочим вариантом: по таким записям владелец правит документы.
- Сбой отката, оставшийся прокси, адаптер, запись VPN или установленная программа — немедленная остановка опасных файлов и сообщение владельцу текстом: что осталось, какой командой проверить, как откатить (`01-ENVIRONMENT.md`, раздел 10; откат в файле A11).
- Если страж не пройден, оркестратор не пытается его обойти: файлы с опасностью получают `BLOCKED`, остальные выполняются.

## 7. Как выполнять ручные файлы

0. Файл с опасностью начинается с проверки: `. C:\lavray-test\env.ps1; Test-TestPc` должна напечатать `True` (маркер `TESTPC_OK` есть, создан на этом ПК, не старше 30 суток). `False` — итог файла `BLOCKED`, ни одного действия. Для файлов с опасностью только в части (M05 и M09 — часть 6, M13 — часть 3 и шаг 4.31, M16 — часть 8) проверка выполняется перед этой частью.
1. Исполнитель — человек за тестовым ПК либо агент с управлением экраном (computer use). Агент перед каждым действием делает снимок экрана, работает только в окнах LAVRay, установщика и Windows, указанных в файле.
2. Шаги — таблицы «Действие / Ожидаемо / Результат». Подписи кнопок и сообщения взяты из словаря `ui/src/lib/dictionaries/ru.ts` дословно; если на экране иначе, это дефект (`minor`) или устаревшая подпись плана (`doc`) — отметьте, что именно видно.
3. Ручные файлы идут в порядке из раздела 5.1. M01 ставит программу, M18 — последний.
4. Отчёт по `templates/REPORT.md`, скриншоты в `results\<ID>\`.
5. Окна установщика и удалителя NSIS и запрос UAC недоступны для UI Automation, если агент (ZCode) запущен без повышения прав: Windows блокирует такой доступ к окнам с повышенными правами (UIPI; типичная диагностика: «UIPI blocks UI Automation from this non-elevated ZCode»). Чтобы пройти эти шаги (M01 пп. 1.1–1.5, 3.1, 6.1; шаги с окнами установщика в M12), запустите ZCode от имени администратора. Если запуск от администратора невозможен, установку и удаление выполняйте тихо (`/S`, через `Start-Process -Verb RunAs`, как в A10) и отметьте шаги, требующие окон NSIS и UAC, как «ждут человека»: проверка результата установки (файлы, реестр, ярлыки) по-прежнему выполняется командами.

## 8. Известные ограничения плана

- Окна установщика, удалителя и UAC недоступны UI Automation из ZCode без прав администратора (UIPI), см. раздел 7, п. 5.
- Часть деталей установщика (тексты окон NSIS, путь ярлыка, поведение при запущенной программе и при понижении версии) в репозитории не зафиксирована; файлы A10 и M01 их записывают как наблюдения.
- Метки окон Windows (`inetcpl.cpl`, «Параметры») зависят от сборки системы; файл M08 сверяет по смыслу.
- Kill switch **системного прокси** реализован в хвостах B (настройка `connect.kill_switch_proxy`, M14). Полная блокировка трафика при падении TUN (WFP, исследование R-1) по-прежнему не реализована: настройка `tun.kill_switch` лишь принудительно включает `strict_route` (в интерфейсе — «Строгая маршрутизация (strict_route)»).
- Часть 2 написана по коду `main` (раздел 1), а не по опубликованному тегу `v0.9.0`: числа проверок привязаны к тегу v0.9.0 (коммит `8093656`): A09 — 222, A12 — 98, A14 — 27, A15 — 129 (128 без права на символические ссылки: одна запись `WARN` вместо двух проверок), A13 — 298; на более поздних тегах чисел может быть больше, меньше быть не должно. Подписи интерфейса сверяйте с тегом `<TAG>`. Скрипты A09, A12, A14, A15, A13 прогнаны на настоящих ядрах, собранных из `main` `773b4e8` (A13 и A09 — ещё и на `80be1e9` и на `dce8ba0`; команда `publish-data` стенда M12 проверена на настоящем ядре, но экран «Обновления» части 13 вживую не прогонялся) (для A12 — со встроенным интерфейсом, собранным на `622a10a`); щелчки по экрану в M09, M10, M11, M12, M13, M14, M15, M16 по реальному приложению не прогонялись, подписи взяты из `ru.ts` соответствующих веток.
- Дефекты, найденные первым прогоном части 2 и исправленные в `470d5f2` (в `main` с `80be1e9`): очистка «Недоступные» не видела результаты проверки (A09, `5.cleanup.*`; M13, шаг 1.3), относительный путь `--data` на Windows не открывал базу, неудачный `import-nekobox` оставлял пустую базу. Проверки остаются в плане как защита от регресса; на сборках до исправления они дают `FAIL` или `WARN`. Все файлы плана по-прежнему передают абсолютные пути.
- Бюджеты производительности из `docs/TEST-PLAN.md` (раздел 2: старт окна, память, CPU) в части 1 не измеряются; из них проверяются только размер установщика и размер загружаемого сразу JS-бандла (≤ 250 КБ gzip, A05, шаг 9; на `v0.9.0` известное превышение D-3, исправлено в 0.9.1).
- Linux-ядро (`lavray-core-linux-*`) проверяется на Linux в WSL (A06, шаг 16): запуск, `GetStatus`, `healthz`; полный набор сценариев (A09 и другие) идёт на Windows-ядре из ZIP. Известный риск: `release-linux.yml` не задаёт версию через `-X`, поэтому Linux-ядро может сообщать константу `internal/version.Version` (в плане — `0.9.0`; если там осталось `0.4.0`, A06 шаг 16 даёт `FAIL` серьёзности `major`).
- Эталонные числа (734 файла в размерной трещотке, 1210 тестовых функций Go в 24 пакетах, 173 файла и 1444 теста vitest, 51 тест скриптов, 457 `#[test]` в Rust) измерены на `v0.9.0` (`8093656`); при росте репозитория их нужно обновлять.
