# LAVRay Update System — спецификация v2.0

Переработана по аудиту 2026-10 (`docs/AUDIT-CLAUDE-2026-10.md` §2.4, сырой отчёт `docs/audit-2026-10/raw/03` §3): v1.0 подписывала только артефакт, держала один ключ и один аккаунт, не пережила бы блокировку GitHub и переход OpenWrt 25.12 на apk. Историю изменений v1.0 см. в git; отличия перечислены в §11.

## 1. Принципы

1. **Никогда не ломать работающий туннель**: обновление применяется только по явному действию пользователя или в спокойном состоянии (не в момент активной сессии, если не подтверждено).
2. **Целостность обязательна**: артефакт без валидной подписи и чексуммы не применяется никогда. Ошибка проверки = безопасный отказ + уведомление.
3. **Откат всегда возможен** — и выполняет его **старая версия**: предыдущая версия сохраняется; маленький rollback-помощник (или служба) ждёт heartbeat новой и откатывает сам, если новая не стартует.
4. **Прозрачность**: пользователь видит, что обновится (приложение / ядро / пресеты / geo-данные), changelog на своём языке, источник-репозиторий.
5. **Каналы**: `stable` (по умолчанию) и `beta`. Смена канала — явное действие.
6. **Доверие даёт подпись, а не хост**: хранилища взаимозаменяемы; allowlist источников берётся из подписанного `sources.json`, а не из кода.
7. **Молчание ≠ нет обновлений**: «проверка не удалась» и «обновлений нет» — разные состояния; клиент показывает «последняя успешная проверка N дней назад».
8. **Обновление переживает блокировки**: сначала через активный туннель, затем напрямую; зеркала на разных провайдерах; офлайн-путь «Установить из файла».

## 2. Модель угроз

| Угроза | Мера |
|---|---|
| Компрометация аккаунта GitHub / CI | Ключи подписи — вне CI и вне аккаунта (§4); подпись релиза — вне CI или в защищённом Environment с ревью; зеркала вне GitHub (`sources.json`); immutable releases |
| Кража ключа подписи | Офлайн root-ключи на аппаратных токенах, threshold 2-из-3; онлайн-ключи со сроком `expires`; отзыв ключа — новая версия `root.json`; процедура аварийной ротации в `docs/SECURITY.md` |
| Freeze (вечный старый манифест) | `timestamp.json` со сроком ≤ 7 дней; клиент предупреждает после 7 дней без успешной проверки, красный статус после 30 |
| Откат на старую подписанную версию (downgrade) | Монотонный `serial` манифеста по каждому каналу; клиент хранит максимум и отвергает меньший |
| Mix-and-match (сборка обновления из кусков разных релизов) | Все артефакты и их sha256 — в одном подписанном манифесте; сборка не применяется при несовпадении любой части |
| Подмена канала (beta вместо stable, `mandatory:true` как DoS) | `product`, `channel` и `mandatory` — внутри подписанного `manifest.json`; клиент отвергает чужой `product`/`channel` |
| Подмена/повтор манифеста (replay) | `serial` + `expires` + подпись trusted comment `product;platform;channel;version;serial` в minisign |
| MITM и DNS-подмена | HTTPS-only; DNS — через DoH ядра; проверка подписи и хеша — после загрузки, на каждом источнике и редиректе |
| Блокировка GitHub (РФ/КНР) | Подписанный `sources.json`: зеркала GitLab/Codeberg, два своих домена на разных провайдерах и регистраторах; jsDelivr — только для метаданных; обновление через туннель |
| Частичная загрузка / обрыв | Контроль `Content-Length`, sha256, докачка (Range) или повтор; обрывки удаляются; копия в защищённый каталог и повторная проверка перед запуском (анти-TOCTOU) |
| Подмена пресетов и geo (тихий обход туннеля) | Пресеты и geo подписываются тем же механизмом и идут с `serial` (§8) |

## 3. Метаданные (TUF-lite)

Четыре подписанных документа. Формат: `{"signed": {…}, "signatures": [{keyid, sig}…]}`.

### 3.1 `root.json` — корень доверия (офлайн)

```json
{"signed":{"type":"root","version":1,"expires":"2027-10-01T00:00:00Z",
  "keys":{"k1":{"alg":"ed25519","pub":"<base64>"},"k2":{"alg":"ed25519","pub":"<base64>"},"k3":{"alg":"ed25519","pub":"<base64>"},
          "t1":{"alg":"ed25519","pub":"<base64>"},"r1":{"alg":"ed25519","pub":"<base64>"}},
  "roles":{"root":{"keyids":["k1","k2","k3"],"threshold":2},"timestamp":{"keyids":["t1"],"threshold":1},
           "manifest":{"keyids":["r1"],"threshold":1},"sources":{"keyids":["r1"],"threshold":1}}},
 "signatures":[{"keyid":"k1","sig":"<base64>"},{"keyid":"k2","sig":"<base64>"}]}
```

> **Фаза 1 (решение владельца 2026-10-23):** `keys` содержит один root-ключ k1, `roles.root = {"keyids":["k1"],"threshold":1}`. Пример выше — целевое состояние 2-из-3; переход без смены формата, версией `root.json` N+1 (процедура — `docs/SECURITY.md` §4.1).

### 3.2 `timestamp.json` — свежесть (онлайн, перевыпускается при каждом релизе)

```json
{"signed":{"type":"timestamp","version":1207,"expires":"<now+7d>",
  "meta":{"manifest-stable.json":{"serial":42,"sha256":"<hex>","length":2817},"manifest-beta.json":{"serial":57,"sha256":"<hex>","length":2903}}},
 "signatures":[{"keyid":"t1","sig":"<base64>"}]}
```

### 3.3 `manifest.json` — содержимое релиза (по одному на продукт × канал)

```json
{"signed":{"type":"manifest","product":"lavray-windows","channel":"stable","serial":42,"expires":"<now+30d>",
  "app":{"version":"1.2.0","minUpgradeFrom":"1.0.0","assets":{"windows-x64":{"path":"v1.2.0/LAVRay-1.2.0-x64-setup.exe","sha256":"<hex>","length":12345678,"minisig":"<minisign>"}}},
  "core":{"version":"1.14.1-lav.1","minApp":"1.2.0"},
  "presets":{"lav-ru":{"rev":43,"path":"presets/lav-ru-43.json","sha256":"<hex>"},"lav-cn":{"rev":5,"path":"presets/lav-cn-5.json","sha256":"<hex>"}},
  "geo":{"path":"geo/2026-10-20.tar.zst","sha256":"<hex>","length":3456789},
  "notes":{"ru":"…","zh":"…","en":"…","es":"…","de":"…"},"mandatory":false},
 "signatures":[{"keyid":"r1","sig":"<base64>"}]}
```

### 3.4 `sources.json` — источники (меняются редко)

```json
{"signed":{"type":"sources","version":3,"expires":"<now+180d>",
  "artifacts":["https://github.com/<org>/lavray-windows/releases/download/","https://codeberg.org/<org>/lavray-windows/releases/download/",
               "https://updates-a.<domain>/lavray-windows/","https://updates-b.<other-domain>/lavray-windows/"],
  "metadata":["https://<org>.github.io/lavray-windows/meta/","https://cdn.jsdelivr.net/gh/<org>/lavray-windows@meta/","https://updates-a.<domain>/meta/"]},
 "signatures":[{"keyid":"r1","sig":"<base64>"}]}
```

**Правила.** Клиент хранит последний `root.version`, максимальный `serial` по каждому каналу и `expires`; отвергает меньший `serial`, чужой `product` или `channel`, истёкший `timestamp`. Ротация root — новый `root.json`, подписанный порогом старых ключей; отзыв ключа — удаление из `keys` в новой версии root. Trusted comment minisign артефакта: `product;platform;channel;version;serial`.

## 4. Ключи и CI

- Фаза 1 (решение владельца 2026-10-23): один офлайн root-ключ у владельца (threshold 1); цель — офлайн root-ключи у 2–3 человек на аппаратных токенах (threshold 2-из-3). Онлайн-ключи `timestamp` и `manifest` — со сроком действия.
- Подпись релиза — вне CI (подписывающий монтаж на машине релиз-инженера) или в защищённом GitHub Environment с обязательным ревью; аппаратная 2FA на аккаунтах; защищённые теги.
- `permissions: read` по умолчанию во всех workflow; actions пинируются по SHA; никаких `ACTIONS_ALLOW_UNSECURE_COMMANDS`; загрузки в CI — только с проверкой хеша.
- Immutable releases (перепубликация артефакта запрещена), provenance-аттестация, SBOM.
- Воспроизводимая сборка: `-trimpath`, `SOURCE_DATE_EPOCH`, стабильные флаги — пользователи и зеркала могут сверить сборку.
- Процедура аварийной ротации ключей — в `docs/SECURITY.md`.

## 5. Алгоритм клиента

1. `timestamp.json` качается **параллельно минимум из двух** источников метаданных (connect 3 с, первый байт 5 с); берётся наибольший валидный.
2. Проверка цепочки: root → timestamp → manifest (подписи, `serial`, `expires`, `product`, `channel`).
3. Артефакт — с любого источника из `sources.json`, с докачкой; проверка длины, sha256, minisign.
4. Копия в защищённый каталог и **повторная проверка перед запуском** (анти-TOCTOU: проверили в `%TEMP%` — запускать оттуда же нельзя).
5. Порядок сети: сначала через активный туннель, затем напрямую; DNS — через DoH ядра.
6. Последний рабочий источник запоминается и пробуется первым.
7. Состояние «последняя успешная проверка N дней назад»: предупреждение после 7 дней, красный статус после 30; до первой успешной проверки текст «нет обновлений» не показывается.
8. Офлайн-путь «Установить из файла»: инсталлятор + `.minisig` + манифест; проверяется той же цепочкой.

Периодичность — не чаще раза в 6 ч, со случайным джиттером, без идентификаторов, через туннель, если он поднят (приватность: запрос не должен палить LAVRay провайдеру).

## 6. Установка и откат по платформам

- **Windows.** Per-machine NSIS + служба LAVRay (TUN без UAC на каждый запуск). Хуки NSIS останавливают сайдкар, снимают TUN и системный прокси [проверь API Tauri для хуков]. Прошлый инсталлятор хранится локально; откат выполняет маленький rollback-помощник старой версии (или служба) по отсутствию heartbeat новой после перезапуска.
- **macOS.** Только из каталога «Программы» (иначе App Translocation заблокирует самообновление — требовать «Переместить в Программы» до включения апдейтера). Developer ID + notarization обязательны до публичного релиза; привилегированный помощник — SMAppService.
- **Linux.** AppImage — встроенный updater, но без TUN либо с systemd-помощником. `.deb` — apt-репозиторий с `signed-by` и `Valid-Until`; обновление строго `apt-get install --only-upgrade lavray` (не общий `apt upgrade`); пул пакетов на Releases/CDN, индекс на Pages (лимит Pages ~1 ГБ).
- **OpenWrt.** **Два фида**: ipk + usign (24.10) и apk + подпись (25.12+); имена пакетов `lavrayd`, `luci-app-lavray`, `lavray-webui` — одинаковые во всех документах. Ключ фида кладётся в `/etc/opkg/keys/` или `/etc/apk/keys/` **до** первого обновления (отпечаток публикуется вне GitHub — сайт/README/Telegram). Скрипт `lavray-update` определяет менеджер, выбирает рабочее зеркало и переписывает единственный активный URL фида. Прошлый пакет хранится локально. Watchdog procd: «нет связи N минут после обновления → откат на прошлый пакет». Обновляются только именованные пакеты LAVRay (не весь мир). Статус и логи — в tmpfs; geo — не чаще раза в неделю; отказ при свободном месте < 2× размера пакета. Подробности шлюза — `docs/OPENWRT-GATEWAY.md`.

## 7. Ядро

Отдельная доставка ядра **разрешена** по тому же манифесту с полем `minApp` (быстрый ответ на CVE ядра и блокировки протоколов; в v1.0 было запрещено). Версия ядра — своя схема (`1.14.1-lav.N`), не semver-сравнение с upstream (по semver `1.14.1-lav.1` < `1.14.1` — сравнение только своей схемой). Обновление ядра требует версию приложения ≥ `minApp`. Политика переноса neko-патчей и гейты обновления upstream — без изменений (см. историю v1.0 §6: аудит changelog → лицензия upstream → патчи → L1/L2 → smoke → рекурсия до нуля → тег `core-<version>`); при каждом обновлении явно проверяется условие `sing-box/LICENSE`:16 об имени.

## 8. Пресеты и geo

Подписываются тем же механизмом (секции `presets` и `geo` манифеста, `serial`/`rev` и sha256). Обновление пресета, у которого есть пользовательские правки, — только через diff/merge, никогда молча. Встроенные наборы `.srs` для пресетов — в поставке (старт без сети, FR-UI-266).

## 9. Каналы

Переход stable → beta — с подтверждением (предупреждение о стабильности). Переход beta → stable — ожидание, пока stable догонит номер версии, либо явный даунгрейд с бэкапом данных (клиент не должен застревать на beta).

## 10. Тесты (обязательный CI-гейт)

Позитив/негатив подписи; просроченный `timestamp`; меньший `serial`; чужой канал/product; недоступный GitHub при доступном зеркале; частичная загрузка; подмена на редиректе; занятые файлы сайдкара; неработающая новая версия → откат; opkg и apk в контейнерах SDK; zip-slip и симлинки в архивах; офлайн-установка из файла; downgrade-артефакт (старый, но валидно подписанный) отвергается.

## 11. Отличия от v1.0 (кратко)

| Было (v1.0) | Стало (v2.0) |
|---|---|
| Подписан только артефакт (Tauri Updater) | TUF-lite: root/timestamp/manifest/sources, serial, expires |
| Один ключ, ротация «с major-версией» | Офлайн root 2-из-3 + онлайн-ключи со сроком; отзыв; SECURITY.md |
| Пиннинг github.com | Доверие подписи; подписанный список зеркал; через туннель |
| `latest.json` без защиты метаданных | `manifest.json` с `product`/`channel`/`serial`/`mandatory` внутри подписи |
| Ядро только в связке с приложением | Отдельная доставка с `minApp` |
| Откат «исполняет новая версия» | Rollback-помощник старой версии + heartbeat |
| OpenWrt — только opkg | Два фида: ipk/usign (≤24.10) и apk/подпись (≥25.12) |
| «Нет сети → нет обновлений» | Статус последней успешной проверки + зеркала + офлайн-файл |
> **Статус реализации (0.1.x).** Это спецификация. Есть библиотека проверки метаданных (`core/internal/updates`, покрыта тестами) и автомат состояний оболочки (`shell/src/updater.rs`, без сети). В приложении обновления не работают: клиент не подключён к ядру, `root.json` и источники не заданы, установки и отката нет, подпись minisign артефакта не проверяется. Доверенный корневой ключ сейчас один (порог 1), «2-из-3» — следующая фаза (§3.1).
