# LAVRay — политика безопасности

Создано по аудиту 2026-10 (`docs/AUDIT-CLAUDE-2026-10.md` §5.5, сырой отчёт `docs/audit-2026-10/raw/03` §3.2). Сопутствующие: `docs/THREAT-MODEL.md`, `docs/UPDATE-SYSTEM.md` v2.0. Поля, отмеченные `[заполнить]`, заполняет владелец до первого публичного релиза.

## 1. Как сообщить об уязвимости

| Канал | Адрес | Примечание |
|---|---|---|
| Основной | GitHub Security Advisories репозитория `lavray` (private vulnerability reporting) | рекомендуется: обсуждение и кредит не уходят в публичный трекер |
| Резервный (если GitHub недоступен) | e-mail **[адрес скрыт]** (PGP-ключ — `[заполнить позже: отпечаток, публикация в README]`) | для аудитории РФ/КНР, где GitHub деградирует; решение владельца 2026-10-23 |

Пожалуйста, сообщайте: версию приложения и ядра, ОС, шаги воспроизведения, влияние, наличие эксплойта. Не открывайте публичный issue для проблем безопасности.

## 2. Сроки ответа

| Этап | Цель |
|---|---|
| Первичный ответ | ≤ 72 часов |
| Оценка и классификация (critical/major/minor по рубрике BUGS.md) | ≤ 7 дней |
| Исправление critical | следующий релиз или хотфикс ≤ 14 дней |
| Исправление major | очередной релиз |
| Публичное раскрытие | после выхода исправления, с кредитом исследователя (если он согласен); embargo ≤ 90 дней |

## 3. Поддерживаемые версии

| Ветка | Статус |
|---|---|
| последняя stable (`1.x`) | поддерживается |
| предыдущая stable | исправления только critical, ≤ 3 месяца после релиза новой |
| beta | best effort |
| всё старее | не поддерживается; обновление обязательно |

До версии 1.0 публичных релизов нет — таблица актуализируется при первом релизе.

## 4. Аварийная ротация ключей подписи обновлений

Основание: компрометация или подозрение на компрометацию любого ключа из цепочки TUF-lite (`docs/UPDATE-SYSTEM.md` v2.0 §3). Цель: скомпрометированный ключ перестаёт приниматься клиентами **без обновления приложения**.

> **Фаза 1 (решение владельца 2026-10-23):** root-ключ один (k1, threshold 1-из-1), держатель — владелец. Схема 2-из-3 ниже — целевая: при появлении 2–3 доверенных держателей выпускается `root.json` N+1 с ключами k1–k3 и threshold 2 (та же процедура, что §4.1). До этого компрометация единственного root-ключа лечится только внеочередным релизом приложения с полной заменой root (шаг §4.2.2). Задача «найти держателей» — не блокирует релиз, отслеживается в RELEASE-CHECKLIST §6.

### 4.1 При компрометации онлайн-ключа (`timestamp` t1 / `manifest`+`sources` r1)

1. Двое из трёх держателей офлайн root-ключей собираются (видео-звонок + обмен токенами по обычной процедуре подписания).
2. Выпускается `root.json` версии N+1: из `keys` удаляется скомпрометированный keyid, добавляется новый ключ (новая пара генерируется на токене, публичная часть — в `keys`); роли переназначаются на новый keyid. Подписывается порогом 2-из-3 **старых** root-ключей.
3. Немедленно выпускаются новые `timestamp.json` (версия+1) и `manifest.json`/`sources.json` (serial+1), подписанные уже новыми ключами.
4. Публикация на все источники метаданных из `sources.json` (включая зеркала вне GitHub — на случай, если скомпрометирован и аккаунт).
5. Оповещение пользователей (см. 4.3). Клиенты подхватывают новый root автоматически: цепочка «старый root (2-из-3) → новый root» валидна по правилам TUF-lite.

### 4.2 При компрометации офлайн root-ключа (одного из трёх)

1. Удержавшийся порог (2 держателя) выпускает `root.json` N+1 без скомпрометированного keyid (threshold остаётся 2-из-2 до ввода нового держателя) — по шагам 4.1.2–4.1.5.
2. Компрометация ≥ 2 root-ключей = катастрофа: приложение с зашитым доверием не отличит подделку. План: внеочередной релиз приложения с новым root (полная замена), объявление через все каналы, отзыв старых манифестов по `expires`.

### 4.3 Оповещение пользователей через `root.json`

- Новая версия root содержит уменьшенный `expires` (например 30 дней вместо года) — все клиенты в течение срока гарантированно перечитают корень и увидят отзыв.
- В следующем `manifest.json` поле `notes` всех языков начинается строкой «Обновление системы безопасности» + баннер `mandatory` не используется (DoS-вектор), вместо этого — заметка в Центре обновлений.
- Дополнительно: запись в RELEASES, закреплённый issue/discussion, сайт, Telegram-канал `[заполнить ссылки]` — каналы вне GitHub обязательны.
- Ответственный за исполнение: владелец; держатели ключей подтверждают участие подписями в журнале инцидента (файл инцидента хранится рядом с процедурой).

## 5. Отпечатки ключей и их публикация

| Ключ | Назначение | Где публикуется (вне GitHub обязательно) |
|---|---|---|
| root k1 (фаза 1; цель — k1/k2/k3, threshold 2-из-3) (ed25519) | корень доверия обновлений | сайт `[заполнить домен]`, README, Telegram, подписанные git-теги |
| timestamp t1 | свежесть метаданных | в `root.json`; отпечаток — там же, где root |
| manifest/sources r1 | содержимое релиза | в `root.json` |
| PGP контакта безопасности | переписка об уязвимостях | сайт, README |
| usign/apk-ключ фида OpenWrt | пакеты 24.10 / 25.12+ | `/etc/opkg/keys/`, `/etc/apk/keys/`; отпечаток — сайт, README, LuCI-страница установки (см. UPDATE-SYSTEM v2.0 §6, OPENWRT-GATEWAY §8) |

Правило: отпечаток считается опубликованным, когда он доступен минимум по двум каналам, хотя бы один из которых не контролируется тем же аккаунтом/провайдером, что и релизы.

## 6. Область действия

Сюда входят: приложение LAVRay, форк ядра, веб-панель и LuCI-приложение, инфраструктура обновлений (CI, ключи, зеркала). Не входят: уязвимости upstream sing-box (репорт в SagerNet/sing-box, крестная ссылка сюда), проблемы сторонних панелей подписок.
