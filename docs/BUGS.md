## 2. Детали, планы исправления в LAVRay и регрессионные тесты

### LNB-01 — Секреты в логах (critical)

**Описание.** Три конкретных утечки в журнал (окно лога + то, что пользователь копирует в отчёт):
1. `sub/GroupUpdater.cpp:484` — после успешной расшифровки Happ-ссылки в лог пишется **весь расшифрованный результат**: `MW_show_log(tr("Happ link decrypted") + ": " + decrypted);`. Результат — обычно URL подписки с персональным токеном или список прокси-ссылок с паролями/UUID.
2. `sub/GroupUpdater.cpp:538-539` — при обновлении подписки вручную (группа ещё не создана, `_sub_gid < 0`) в лог пишется сам URL подписки (`groupName = content`), включая токен в query.
3. `sub/GroupUpdater.cpp:543` — в лог ошибки запроса пишется **тело ответа** `resp.data` — произвольные данные с сервера подписки.

README форка признаёт это («Известное ограничение: расшифрованный адрес подписки может попадать в журнал», раздел «Что нельзя публиковать без проверки»; «Открытые вопросы»: «защита персональных адресов в журналах нуждаются в улучшении»).

**План в LAVRay.** Единый слой санитайзинга логов: функция `redactForLog()` для всех «пользовательских» строк — вырезание userinfo из URL (`https://user:pass@host` → `https://host`, query-параметры с типовыми именами `token/key/password/psk` → `[СКРЫТО]`), замена содержимого ссылок `ss://… vmess://… vless://… trojan://… happ://…` на `<link:тип>`. Логировать только хост подписки, никогда — путь/query/расшифрованный контент. Кнопка «Копировать лог» должна прогонять текст через тот же санитайзер.

**Регрессионный тест.** Юнит-тест санитайзера на таблице векторов (URL с токеном, ссылка vless с UUID, многострочный вывод Happ, тело ответа с паролями) + контрактный тест: подписать мок-подписку и happ-ссылку, утвердить, что ни одна строка лога не содержит исходный токен/UUID/расшифрованный URL (проверка `assert(logNotContains(secret))`).

### LNB-02 — Обновление без проверки целостности (critical)

**Описание.** Полная цепочка обновления не проверяет ни подпись, ни чексумму:
- `go/grpc_server/update.go:86-113` — ядро скачивает `update_download_url` (GitHub release) в `../nekoray.zip` и на этом всё: статус HTTP не проверяется (404/HTML сохранится как zip), сравнение с ожидаемым размером/хешем отсутствует.
- `go/cmd/updater/updater.go:36-58` — updater распаковывает zip без какой-либо верификации и переносит файлы поверх работающей установки.
- `go/cmd/updater/go.mod` — `github.com/codeclysm/extract v2.2.0+incompatible` (2019 г.): в этой версии нет защит от zip-slip (записи `../../` в архиве пишутся вне каталога установки). Транспорт защищён TLS, но компрометация аккаунта/релиза или подмена файла в канале — молчаливое выполнение произвольного кода от имени пользователя. README: «Самообновление не прошло полного сквозного теста…»; SHA-256 автор сверяет вручную.

**План в LAVRay.** Обязательная верификация перед распаковкой: манифест обновления с чексуммами всех артефактов + подпись (minisign/ed25519, ключ зашит в бинарник) — проверка до распаковки и повторно после; отказ с понятной ошибкой при несходстве. Заменить `codeclysm/extract v2` на современную библиотеку или `archive/zip` со своей проверкой имён записей (`filepath.Clean`, запрет `..` и абсолютных путей, запрет симлинок).

**Регрессионный тест.** (а) Тест-вектор: zip с записью `../../evil.dll` → распаковка обязана отклонить архив; (б) подмена одного байта в артефакте после подписи → отклонено; (в) отсутствие/битая подпись → отклонено; (г) HTTP 404 при скачивании → ошибка, файл не создан.

### LNB-03 — Обновление без отката и без атомарности (major)

**Описание.** `go/cmd/updater/updater.go:60-73`: перед переносом удаляются **все** `*.dll` и `*.dmp` (`removeAll("./*.dll")`), затем `Mv("./nekoray_update/nekoray", "./")`. Если Mv упадёт на середине (занятый файл, нет прав), установка остаётся наполовину обновлённой, DLL уже удалены — программа мертва; сообщение предлагает «закройте приложение и запустите updater снова». Бэкапа старых файлов нет. `go/cmd/updater/main.go:57-62` — `Copy()` игнорирует ошибки чтения/записи (молча). README: «Надёжного автоматического отката при неудачном обновлении также нет».

**План в LAVRay.** Атомарное обновление по схеме staging: распаковка в отдельный каталог → верификация (LNB-02) → перенос текущих файлов в `backup/<timestamp>` → rename staging → запуск → при первом старте новая версия помечает обновление успешным, иначе автоматический откат из backup. Ни один файл не удаляется до успешного завершения rename. Ошибки на любом шаге = откат + внятное сообщение. Плюс: updater обязан логировать свои действия в файл.

**Регрессионный тест.** Интеграционный тест на копии установки: (а) инжекция сбоя посреди Mv (файл с эксклюзивным локом) → после прогона установка откатана и запускается старая версия; (б) успешный сценарий → новая версия стартует, backup создан; (в) сбой верификации → файлы не тронуты.

### LNB-04 — Секреты в открытом виде на диске (major)

**Описание.** Профили (`config/profiles/<id>.json`), группы с URL подписок (`config/groups/<id>.json`), общий конфиг (`config/nekoray.json`) сохраняются как обычный JSON: пароли прокси, UUID, приватные ключи, `inbound_auth` (`main/NekoGui.cpp:231`), `core_box_clash_api_secret` (`main/NekoGui.cpp:283`). Шифрования нет вообще (grep по `encrypt/DPAPI` — пусто). Путь формирования: `db/Database.cpp:271` (`profiles/%1.json`). Это же относится к `vpn/sing-box-vpn.json` с паролем inbound.

**План в LAVRay.** Хранить учётные данные в системном хранилище (Windows DPAPI / Credential Manager; Linux libsecret), в JSON-конфигах — только ссылки на записи хранилища; права `0600` на файлы конфигов; опция «экспорт» с явным предупреждением. Как минимум — DPAPI-обёртка над секретными полями.

**Регрессионный тест.** Тест персистентности: создать профиль с паролем → перезапуск → пароль читается; сканирование каталога config на plaintext-вхождение пароля (`grep`-подобный тест) — не найдено.

### LNB-05 — SSRF / file:// через URL подписки (major)

**Описание.** `NetworkRequestHelper::HttpGet` (`main/HTTPRequestHelper.cpp:13-48`) принимает любой `QUrl` без проверки схемы и адреса. URL подписки вводится пользователем/импортируется из группы. `QNetworkAccessManager` умеет `file://` — подписка с `file:///C:/Users/.../x` читает локальный файл и отдаёт в парсер; `http://127.0.0.1:…`, `http://169.254.169.254/…` (метаданные облака) — зондирует внутреннюю сеть с машины пользователя, а тело ответа утекает в лог (LNB-01.3). Политика редиректов `NoLessSafeRedirectPolicy` (строка 39) допускает http→http редиректы — начальный `https` может «спуститься» до http на цепочке? (NoLessSafe запрещает https→http, но начальный http остаётся http) — перенаправления не фильтруются по целевому хосту/IP. Прокси для запроса берётся локальный inbound, иначе запрос идёт напрямую — SSRF выполняется из доверенной сети пользователя.

**План в LAVRay.** Валидатор URL подписки до запроса: только `http/https`; домен резолвится (через системный резолвер) и адрес проверяется на приватность/loopback/link-local/unique-local (кроме случая явной галки «разрешить локальные адреса»); контроль редиректов своими руками (максимум N, каждая цель — через тот же валидатор); лимит размера ответа (LNB-12).

**Регрессионный тест.** Таблица URL: `file:///etc/passwd`, `http://127.0.0.1:19810`, `http://169.254.169.254/latest/meta-data`, `http://10.0.0.1`, редирект на `http://127.0.0.1` — все отклонены человекочитаемой ошибкой; `https://example.com/sub` — разрешён.

### LNB-06 — Нет таймаутов gRPC + mutex-UB (major)

**Описание.** `rpc/gRPC.cpp`: `Client::Start` (218), `Stop` (232), `Update` (287), `Test` (274) вызывают `Call(...)` с `timeout_ms = 0` → таймер-аборт не создаётся (109-119). Если ядро зависло (не ответило), вызов висит вечно. Ожидание реализовано как `QMutex lock; lock.lock(); runOnUiThread([&]{ ...; lock.unlock(); }); lock.lock(); lock.unlock();` (172-183) — QMutex используется как семафор и **разблокируется из другого потока** (UB для QMutex), а при потере callback'а — вечное зависание рабочего потока. Следствия: «Starting profile…» никогда не завершается, `mu_starting` остаётся заблокирован (mainwindow_grpc.cpp:351-392) — приложение в мёртвом состоянии. Существующий костыль — модальное окно «Если долго нет ответа, перезапустите программу» через 5 с (376-379, 468-471) — признаёт проблему частью UX.

**План в LAVRay.** Контрактные тесты генератора конфигов: для каждого поддерживаемого протокола и каждой комбинации ключевых опций (reality/uTLS/flow, ws-early-data, mux, uot, hop-порты, ALPN…) — golden-JSON + автозапуск `check` ядра в CI; таблица совместимости «протокол × опция» ведётся как код.

**Регрессионный тест.** CI-job: перебор матрицы профилей → `core check` exit 0 + diff с golden; любое изменение схемы конфига без обновления golden — красный тест.

### LNB-24 — Правовой статус Happ-материалов (minor, правовой)

### LNB-25 — Подписка → запись файлов → RCE (critical)

**Серьёзность:** critical (P0). **Добавлено аудитом 2026-10** (сырой отчёт 03 §2, N-01).

**Где.** `sub/GroupUpdater.cpp:61-69`; `fmt/AbstractBean.cpp:14-15`; `db/ConfigBuilder.cpp:32-70, 82-89`; `ui/mainwindow_grpc.cpp:162`; `sing-box/experimental/clashapi/server_resources.go:97-125`.

**Сценарий.** `nekoray://`-ссылка из подписки загружает все поля профиля, включая `c_cfg` (custom config), `c_out` и `core=internal-full`; `MergeJson` не фильтрует ключи. При `experimental.clash_api.external_ui(+_download_url)` sing-box скачивает zip и распаковывает его без защиты от `..` (тег `with_clash_api`). Подписку выдаёт полудоверенная сторона; узел из подписки попадает в «Тест задержки» группы (`ui/mainwindow_grpc.cpp:162` — `c_cfg` мержится и в тестовый конфиг) → запись в автозагрузку = выполнение кода. Цепочка собрана по коду, не воспроизведена [проверь].

**План в LAVRay.** Импортированным профилям игнорировать `c_cfg`, `c_out`, `core`, `cmd` (ручное включение — только с diff и подтверждением, FR-UI-257); allowlist ключей MergeJson (без `experimental`, `log.output`, чужих `inbounds`); патч форка sing-box: запрет `..`, абсолютных путей и симлинков + лимит размера в `downloadZIP`.

**Регрессионный тест.** Подписка с `nekoray://`-профилем, содержащим `c_cfg` с `external_ui_download_url` → поля отброшены, предупреждение в предпросмотре; zip с записью `../../x` → распаковка отклонена; golden-тест allowlist.

### LNB-26 — Повышение прав через файлы пользователя (major)

**Серьёзность:** major (P1). **Добавлено аудитом 2026-10** (сырой отчёт 03 §2, N-02).

### LNB-29 — Деструктивное обновление подписки (major)

## 4. Рекомендации по качеству для архитектуры LAVRay

Заложить с первого дня (каждый пункт закрывает перечисленные баги):

1. **Redaction-слой логов** (LNB-01, LNB-22): единая точка входа `log.sanitize()`: userinfo URL, query-токены, содержимое share-ссылок/happ, JSON-поля `password/token/uuid/secret/private_key`. Тест golden-векторов + отрицательный тест «секрет не встречается ни в одной строке лога».
2. **Таймауты как контракт** (LNB-06, LNB-07, LNB-19): любой сетевой/IPC-вызов получает дедлайн и отмену; никаких вечных ожиданий на мьютексах; состояния start/stop/update — конечные автоматы с таймаутами переходов и наблюдаемостью.
3. **Обновления с доказуемой целостностью** (LNB-02, LNB-03, LNB-07, LNB-11): подпись ed25519/minisign + чексуммы, staging-каталог, атомарный swap, автоматический откат при первом неудачном старте, semver-сравнение,-docачка/ретраи, чистка битых частичных файлов.
4. **Валидация URL подписок** (LNB-05, LNB-12): whitelist схем, запрет приватных/loopback/link-local целей, контроль редиректов, лимит размера и числа профилей, опциональный «allow local» с явным флагом.
5. **Контрактные тесты генератора конфигов** (LNB-08, LNB-23): матрица протокол×опция → golden JSON → прогон через валидатор ядра в CI; миграторы старых форматов настроек (DNS) с golden-тестами.
6. **Fuzzing парсеров** (LNB-13, LNB-15, LNB-16, LNB-17): go-fuzz/libFuzzer-цели для happ, base64-детектора, ссылок всех протоколов, Clash YAML; свойство «мусор не паникует и возвращает структурированную ошибку»; таблицы векторов в репозитории.
7. **Модель конкурентности** (LNB-10, LNB-20): логика в одном event-loop, обмен сообщениями по значению; запрет cross-thread lock/unlock (линтер + TSAN в CI); порты — только через bind-с-проверкой, без TOCTOU.
8. **Хранилище секретов** (LNB-04, LNB-18): DPAPI/keyring для учётных данных, права 0600, CSPRNG для всех токенов, автосекрет Clash API, constant-time compare, секреты в подпроцессы — только через stdin/pipe.
9. **Диагностика краха ядра** (LNB-21, U-04, U-13): явные состояния CoreDown/RateLimited в UI, автоматический сбор последнего вывода ядра, кнопка «перезапустить», сброс зависших состояний, минидампы.
10. **Управление процессами VPN** (LNB-09): Job Object/process group, точечный kill по PID, никаких убийств по имени образа.
11. **Процесс релиза** (LNB-24, U-01, U-09): NOTICE/SBOM со списком заимствований и лицензий, включённые Issues или Discussions как канал отчётов, подпись сборок, автогенерация чексумм в релиз + их проверка апдейтером.
12. **Тестируемость UI-состояний** (U-03, U-07, U-11): state-machine-тесты (старт/стоп/крах/обновление), password echo mode по умолчанию во всех полях секретов.
13. **Allowlist ключей MergeJson** (LNB-25, аудит 2026-10): пользовательский `custom_config` мержится только по белому списку ключей; `experimental`, `log.output`, чужие `inbounds` и raw-поля форка — запрещены; для импортированных профилей мерж `c_cfg`/`c_out` отключён по умолчанию.
14. **Запрет `c_cfg` у импортированных профилей** (LNB-25, FR-UI-257): подписка и share-ссылки не могут доставить собственную конфигурацию ядра; ручное включение — с показом diff и подтверждением.
15. **Привилегированный помощник с правами** (LNB-26, LNB-27, FR-UI-269): маленькая служба Windows / systemd-unit / SMAppService; принимает только валидированный конфиг по аутентифицированному IPC; UI и парсеры работают без прав; никаких скриптов и конфигов из каталога пользователя в elevated-контексте.
16. **Страж восстановления** (LNB-03/LNB-21, FR-UI-270): после краха ядра или UI следующий старт снимает TUN-адаптеры, маршруты, системный прокси и DNS-перехват; хранит «грязный» флаг на диске атомарно.
17. **TUF-lite для обновлений** (LNB-02/03/07/11, LNB-30): подписанные метаданные `root`/`timestamp`/`manifest`/`sources`, монотонный serial, зеркала, обновление через туннель, откат силами старой версии — полная спецификация в `docs/UPDATE-SYSTEM.md` v2.0.
